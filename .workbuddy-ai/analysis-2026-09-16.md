# microfeed 项目功能分析与改进建议

> 分析日期：2026-09-16
> 分析基础：源码通读 + 本轮实际参与的 i18n / 主题 / 部署 / CLI 工作的一手经验
> 结论均附**可核对的证据**（文件、行数、命令输出），不含泛泛而谈

---

## 一、项目定位与功能全景

### 定位

**microfeed 是一个自托管在 Cloudflare 上的「agentic CMS」**——面向技术型个人，
无需自己运维服务器，就能把音频、视频、图片、文档、博客、外链发布成
**Web + RSS + JSON Feed** 三种形态。

一句话概括其差异化：**同一个内容，既能让人在后台编辑，也能让 AI 代理通过 CLI 管理。**

### 核心功能矩阵

| 能力 | 实现 | 备注 |
|---|---|---|
| **多形态发布** | 条目（item）支持音频/视频/图片/文档/外链 | 一个条目可带一个主媒体附件（= RSS enclosure）+ 独立封面图 |
| **独立页面 Pages** | 顶级路径 + 导航 + 富文本 | 内置 404 页受保护（可改正文，不可改路径/状态） |
| **搜索** | D1 全文检索，AND 语义、引号精确短语、容错标题匹配 | 有归一化/索引就绪状态 |
| **主题系统** | 版本化、不可变、D1 为运行时真相源 | 7 个内置主题 + 自定义/本地目录/GitHub 安装 |
| **管理后台** | Astro + React islands | 内容、主题、站点文件、API 密钥、webhook 浏览器 |
| **公开 API** | OpenAPI 3.1，Bearer 认证，幂等键 | 文档用 Scalar 渲染，含 LLM 友好的 `llms.txt` |
| **Webhook** | Standard Webhooks 签名，Cloudflare Queue 投递 | 事件目录 + 投递重试策略 |
| **媒体** | R2 + 预签名同源上传 | 上传前预留幂等键 |
| **站点文件** | 可编辑的顶级文本文件（robots.txt 等） | 分「生成型」与「自定义型」，生成型可重置 |
| **管理 CLI** | 16 个命令（init/connect/deploy/theme/snapshot/auth/domain/destroy…） | 每套安装生成独立 wrangler 配置 |
| **国际化** | 后台中英双语（1538 键 ×2） | 公开面跟随访客 `Accept-Language` |

### 技术栈与规模

- **运行时**：Cloudflare Workers + D1（SQLite）+ R2
- **框架**：Astro（SSR）+ React 19 + Tailwind + shadcn/base-ui
- **关键库**：better-auth（认证/Passkey/OAuth）、kysely（D1 查询）、
  zod + zod-openapi、i18next、mustache（主题模板）、Scalar（API 文档）
- **规模**：`src` 386 文件 / **约 64,200 行**；`manage-cli` **约 15,900 行**；
  测试 **134 个文件**（单测 118 文件 / 795 用例）

### 质量门禁（`yarn check`，顺序执行）

```
theme-kit:test → theme-kit:pack-check → lint:openapi → typecheck
→ cli:check → test → build → wrangler deploy --dry-run → docs:check
```

**这套门禁是项目最扎实的部分**：覆盖主题契约、OpenAPI 规范、类型、
CLI 包完整性、单测 + Worker 测试、构建产物、以及真实 Worker 打包校验。
CI 另加 `yarn install --immutable` 保证 lockfile 一致。

## 二、改进建议

按「收益/成本」排序，前四条是我建议优先做的。

### 🔴 P1 — `translate()` 未命中键时**静默降级**，是真实事故来源

**证据**（`src/shared/i18n/index.ts:68`）：

```ts
const template = table[key] ?? flattened[DEFAULT_ADMIN_LANGUAGE][key] ?? key;
```

键不存在时**原样返回键名**——用户界面会直接显示 `errors.dashboard.lockedTitle`。

**为什么危险**：`tsc` 通过 **≠** 键正确。本轮的 OpenAPI 全译就是靠我额外写的
「完整性 + 无死条目」校验才发现一处笔误（`used for` vs `used by`）。
这种错误**类型系统抓不到、测试也未必覆盖**，但会直接暴露给用户。

**建议**：

1. 开发构建下未命中时 `console.warn`（或抛错），生产才降级；
2. 把「键存在性 + 中英一致性 + 占位符集合」三项校验**正式纳入 `yarn check`**
   （目前只存在于我的本地脚本里）；
3. 中期考虑用 **key 类型化**（`translate` 的入参收敛为 `keyof typeof en`），
   让 `tsc` 直接抓住拼错的键——这是根治。

### 🔴 P1 — 缺少 lint / formatter，且存在**过时配置**

**证据**：

- `package.json` **没有 `lint` 脚本**，依赖里 **0 处 eslint**；
- 但仓库里**存在 `.eslintignore`**（已失效的死配置）；
- 无 `.prettierrc`（虽装了 `@astrojs/check`，但那只管 Astro/TS 语法）。

**影响**：CI 只能挡类型与测试错误，挡不住风格漂移、未使用变量、
可疑模式（如 `==`、浮动 Promise、误用 `any`）。长期会积累成
「同一件事在不同文件有 5 种写法」。

**建议**：二选一——① 正式引入 ESLint（flat config）+ Prettier 并接入 `yarn check`，
删掉失效的 `.eslintignore`；② 若刻意不做 lint，**至少删掉死配置**，
避免后来者以为有 lint 而放松警惕。

### 🟠 P2 — `manage-cli/commands.ts` **8442 行**，已到可维护性红线

**证据**：`wc -l` 显示 `manage-cli/commands.ts` **8442 行**，
是第二大文件（`theme.ts` 1951 行）的 4.3 倍。

**影响**：本轮修 `--preview` 那个 bug 时，定位 `dashboardAuthCommand`
需要跨文件追踪；8442 行的单文件让「改动影响面」难以评估，
也让 review 成本陡增。

**建议**：按命令拆分为 `commands/{deploy,theme,auth,snapshot,destroy}.ts`，
共享逻辑进 `lib/`。**纯机械重构，不改行为**，有 134 个测试文件兜底，风险可控。

### 🟠 P2 — 部署配置有**两个来源**，是明确的踩坑点

**证据**：根 `wrangler.jsonc` 顶部注释写明
*"Build and type-generation defaults only. `yarn manage` generates and uses a
complete per-installation Wrangler configuration for every deployment."*

**风险**：不熟悉的人（或 AI）直接 `wrangler deploy` 会**缺 D1/R2 绑定与 secrets**，
可能搞坏线上站点。本轮我差点踩到，是读到注释才避开的。

**建议**：把风险从「靠注释」变成「靠机制」——例如给根配置加一个
明显无效的占位 `name`，或在 `wrangler.jsonc` 无法表达的地方用一个
`scripts/guard-deploy.mjs` 在误用时直接报错。

### 🟡 P3 — 国际化有三处**手工同步**的真相源

| 位置 | 规模 | 同步方式 |
|---|---|---|
| `src/shared/i18n/en.ts` | 1538 键 | 手工 |
| `src/shared/i18n/zh-CN.ts` | 1538 键 | 手工（`DeepStringify` 编译期镜像形状） |
| `OpenApiTranslations.ts` | 131 条源串 | 手工（按英文原文为键） |

**评价**：OpenAPI 那份用「英文源串为键」的设计**很聪明**——131 条覆盖 295 处，
且文档重构不失效。但它引入了**第三个**需要维护的翻译表，
且与 i18n 的键体系**互不相通**。

**建议**：短期把三处的一致性校验统一成一个脚本；
中期评估是否让 OpenAPI 描述直接复用 i18n 键（代价是 295 个键，但只维护一套机制）。

### 🟡 P3 — 预览环境的能力缺口

**证据**（本轮实测）：

- `yarn manage domain --help` 明写 **"Refuses preview environments"**，
  所以预览版只能挂在 `*.workers.dev` 上；
- 预览版锁定页给出的命令**漏了 `--preview`**（我本轮已修，提交 `a88b469`），
  照抄会去改**生产**的管理员凭据。

**建议**：让 `domain` 支持 preview（或提供等价的预览域名命令）。
这不只是便利问题——**没有自定义域名时，预览环境在部分网络下无法验证**
（本轮就因 `*.workers.dev` 被 DNS 劫持而卡住，最后靠绑 `preview.881019.xyz` 才验收成功）。

### 🟡 P3 — 测试基线里有 **2 个恒定的环境性失败**

**证据**：全量跑恒为
`manage-cli/instance-management` 与 `manage-cli/webhook-lifecycle` 各 1 个失败
（safe-delete 闸导致），隔离复跑 227 用例全绿。

**影响**：每次都要人工判断「这 2 个是已知的，不是回归」——
新人或 CI 上会浪费排查时间，也**削弱了测试信号的可信度**。

**建议**：把这两个用例与文件系统删除解耦（或用临时目录 + 显式跳过），
让基线变成**全绿**。一个「永远有 2 个红」的测试套件，长期会让人习惯性忽略红灯。

### 🟢 P4 — 主题系统的一处不完整

**证据**（本轮实测）：把 `feed-zh` 迁入仓库时发现——
未注册进 `BUNDLED_THEME_CATALOG` 的主题目录**是完全惰性的**
（所有脚本都经 catalog 枚举，无 `readdir`），这**很好**；
但内置主题还额外要求 `released-packages.json`（发布台账）与 `src/` 构建链，
而「手工写模板」的主题**无法满足**，于是只能停在「入仓但不注册」。

**建议**：要么正式支持「bundled 但无构建链」的主题形态，
要么在 `themes/README.md` 里把这条边界写清楚（本轮我已补了一段说明）。

### 🟢 P4 — 少量 TODO 与已知缺口

源码中仅 5 处 TODO，**数量很少是好事**，但其中两条值得处理：

- `MediaFileUtils.ts:20` 与 `MediaManager/index.tsx:323`：
  **内容类型靠扩展名猜**，TODO 说应改为 HEAD 请求获取。
  这会影响媒体附件的 `mime_type` 正确性（RSS enclosure 依赖它）。
- `AdminImageUploaderApp/index.tsx:217`：**上传失败没有错误提示**。
  静默失败对用户很不友好。

## 三、总体评价

**做得好的地方**（不是客套，都有证据）：

1. **质量门禁完整度罕见**：9 道检查覆盖主题契约、OpenAPI、类型、CLI 包、
   测试、构建、真实 Worker 打包、文档构建。多数同规模项目只有 typecheck + test。
2. **文档覆盖扎实**：`docs/` 30+ 篇，分 start-here / dashboard / manage / api /
   automation / reference 六个面向，且有 `docs:check` 保证文档能构建。
3. **「不可变版本 + D1 为真相源」的主题模型**是正确设计——
   避免了很多 CMS 主题升级把站点搞崩的问题。
4. **对外契约有意识**：OpenAPI 由 TS 单一真相源产出 JSON/YAML/`llms.txt`，
   公开面与后台分离，i18n 不污染契约。
5. **AI 友好是真实投入**：`.agents/skills/` 内置主题开发技能、
   `llms.txt`、CLI 的机器可读 `--json` 输出——不是营销词。

**最该改的三件事**：

| 优先级 | 事项 | 理由 |
|---|---|---|
| 1 | **让 i18n 键错误不再静默** | 唯一会**直接暴露给终端用户**的缺陷类型 |
| 2 | **补 lint 或删死配置** | 当前无风格防线，且存在误导性死文件 |
| 3 | **拆 `commands.ts`（8442 行）** | 已到影响改动安全性的程度 |
