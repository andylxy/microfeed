## 🚨 事故与恢复：`git commit` 后分支引用被抹掉（2026-09-16 10:09）

### 症状

`git commit` **报告成功**（`[chore/admin-i18n cf835c7] … 5 files changed`），
但紧接着 `git log` 为空、`git status` 显示 **985 个文件被暂存为 `A`**，并报：

```
fatal: your current branch 'chore/admin-i18n' does not have any commits yet
```

### 诊断（只读）

```bash
cat .git/HEAD                  # ref: refs/heads/chore/admin-i18n  ← 正常
find .git/refs -type f         # 只有 main 和 remotes/origin/HEAD
                               # ⇒ refs/heads/chore/admin-i18n 不见了
ls .git/objects/pack/          # pack 17MB 完整
find .git/objects -type f -not -path "*/pack/*" | wc -l   # 449 个松散对象
find .git/logs -type f         # logs 完好 ✅
tail .git/logs/HEAD            # ← 关键：reflog 完整记录了整条链
```

**reflog 里能直接读到最新提交**：`c5689763 → cf835c7c commit: Translate the admin API explorer…`

**结论：只有「分支引用文件」被删，对象与 reflog 全在 ⇒ 零数据丢失。**

### 恢复（两步）

**① 先核验对象存在**（别急着写引用）：

```bash
git cat-file -t <sha>     # 必须回 commit
```

**② 写回引用——但 `git update-ref` 在本环境会「假成功」**：

```bash
git update-ref refs/heads/chore/admin-i18n <sha>   # 退出码 0
ls .git/refs/heads/                                # ❌ 文件根本没落盘！
```

⇒ **必须直接写文件**：`.git/refs/heads/chore/admin-i18n` 内容为 `<40位sha>\n`
（用 Write 工具写，不要用 shell 重定向）。

**复核只看 `git rev-parse HEAD`，绝不看命令回显**（技能里的原话：本环境
`fetch` / `update-ref` 写引用会假成功）。

### 恢复后验收（逐项实测）

- `git log --oneline` → **435 个提交，exit 0**，走到 `c4fa3d4 Initial commit`；
- 6 个提交 `git show --stat` 全部 ok；
- 工作区恢复正常（985 个暂存文件消失），只剩预期的 1 个改动；
- `git branch -vv`：`chore/admin-i18n` → `cf835c7`，`main` → `[origin/main] b510bb2`。

**备份**：`.git/refs`、`.git/logs`、`packed-refs` 已备份到

### ⚠️ 已确认可复现：**本环境每次 `git commit` 都会吃掉分支引用文件**

第二次提交（bug 修复 `a88b469`）**原样重现**：提交报成功、引用文件又被删。
⇒ 这不是偶发，是**稳定行为**。与用户记录的 2026-09-12 XiHan.BasicApp 事故同源。

**固化的提交流程（每次提交后立刻做）**：

```bash
git commit -m "…"
git rev-parse HEAD                      # 若 fatal ⇒ 引用被吃了，走下面

git cat-file -t "$SHA"                  # 先核验是 commit 对象
# 再用 Write 工具直接写 .git/refs/heads/<branch>，内容 "<SHA>\n"

```

（"branch does not have any commits yet" + 把整个工作区显示成已暂存），
**不要被它带偏**——对象和 reflog 通常完好，恢复成本极低。

## 根因再深入：为什么"只有 AI 操作出问题"（用户提问）

用户追问：**没要求删除，为什么会有删除操作？为什么手动操作从来没事？**

### 做了 4 组对照实验，逐条排除

| 实验 | 结果 |
|---|---|
| `.git` 副本放 `C:\...\Temp\` 下，跑同样的 `git commit --allow-empty` | **完全正常**，引用没被吃 |
| 真仓库里**只跑一条纯净 `git commit --allow-empty`**（不夹带任何 rm） | **仍被吃** ⇒ 与 commit 本身绑定 |
| `env -u BASH_ENV -u CODEBUDDY_SESSION_ID -u CODEBUDDY_SAFE_DELETE_*` 后提交 | **仍被吃** ⇒ **不是** shell 的 `rm` 包装 |
| `gc.auto=0` / 无钩子 / 无 `packed-refs` 依赖 / 嵌套分支名 | 全部排除 |

### 结论

**本沙箱在文件系统层拦截「工作区内」的删除，改为移进 Windows 回收站。**
关键特征：**与路径相关**（工作区被拦、`Temp` 豁免）、**与环境变量无关**
（`env -u` 关不掉）。git 提交时的引用维护会删 lock 文件并清理 ref 命名空间目录，
这些删除被改写成"搬运"，**引用连同父目录 `refs/heads/<ns>` 一起离开仓库**。

回收站 `$I` 时间戳与提交**同一分钟**，条目为：
`refs/heads/chore`（目录）、`HEAD.lock`、`index.lock`、`packed-refs.lock`、`AUTO_MERGE.lock`。

**为什么手动没事**：这层拦截只作用于 AI 会话/工作区，你自己的终端没有它。

### 顺带查清的另一套机制（不是本次元凶，但要知道）

`BASH_ENV` 指向 `shell-runtime-bash-env.sh`，给**每个 bash 子进程**注入
`rm`/`unlink`/`rmdir` 函数（`safe-bin` 包装，PATH 第 2 位）。
但包装脚本有判据：`[ -z "$CODEBUDDY_SESSION_ID" ] && exec "$REAL_RM" "$@"`
——**无沙箱会话直接放行**。所以这是"另一个"保护层，不是引用丢失的原因。

### 精简了提交流程（用户指出备份/恢复浪费算力）

实测五次证明：**只有那 41 字节的引用指针会被移除，对象与 reflog 从未受损**。
⇒ 全量备份是多余的。`safe-commit.sh` 已改为**默认不备份**（`--backup` 可选）：
精确 add → commit → 复核（被吃则从 reflog 重写）→ 校验可读。
另修了一个缺陷：引用**已**缺失时原先会直接退出，现在会先从 reflog 补回引用再继续。

三条路径均实测通过：正常 / 引用已缺失自动恢复 / 拒绝 `main`。
