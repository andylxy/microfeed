## 自查发现并修掉：切换入口会在没有格式回调的调用方造成数据损坏

`AdminRichEditor` 有**三个**调用方，prop 契约并不同：

| 调用方 | `bodyFormat` | `onFormatChange` |
|---|---|---|
| `EditItemApp`（条目） | ✅ `item.content_format` | ✅ |
| `EditChannelApp`（频道简介） | ❌ | ❌ |
| `PageEditorApp`（站点页面） | ❌ | ❌ |

我加的「改用 Markdown 编辑本章」按钮原本只按 `!isMarkdown` 判定 → 在频道/页面也会出现。
点了之后 `onFormatChange` 是 undefined（原实现是可选调用），于是**正文被改成 Markdown
但格式无处记录** → 前台按默认 html 处理 → `## 标题` 当字面量输出。**数据损坏。**

修法（两层）：① UI 层 `canRecordFormat = typeof onFormatChange === "function"` 才显示按钮；
② 处理层 `onConfirmSwitchToMarkdown` 开头直接 return（纵深防御）。
新增 2 例：`不提供时按钮不出现` / `不提供时确认也不改动正文`。
**已验证去掉 UI 守卫后测试会失败**（处理层守卫仍在，所以另一例仍过——两层各管各的，这是有意的）。

**教训（重要，可复用）**：往共享组件加新能力时，必须逐个核对所有调用方的 prop 契约。
`AdminRichEditor` 是「条目能用、频道和页面用不了」的典型：任何依赖 `content_format`
的新功能都要显式门控在 `onFormatChange` 存在时，否则会在没有该字段的表上静默损坏数据。

## 自查发现并修掉（其二）：`htmlSource` 陈旧会把旧 HTML 写回、吞掉 Markdown 编辑

`htmlSource` 在构造函数里**只算一次**。原本安全（那时正文只在可视化/HTML 源码两种模式间改，
每次改都同步 `htmlSource`）。但我新增的 Markdown 路径会改正文却不碰它 →

```
转成 Markdown → 编辑 → 点回「HTML 源码」→ 显示的是转换前的旧 HTML
→ 只要改一个字，onHtmlChange 把整段旧 HTML 写回 → Markdown 编辑全部丢失
```

修法：`onModeChange('html')` 时重新按当前正文算一遍（抽成 `htmlSourceFor()`，
构造函数复用同一个函数，避免两处各写一遍）。
**先写测试跑出红色再修**——这条测试现在锁住了这个回归。

**教训**：给编辑器加"第三种改正文的方式"时，要检查**所有**缓存了正文副本的地方。
`htmlSource` 就是这样一个副本，它的不变式是"始终等于当前正文"，而新路径打破了这个不变式。

## 自查发现并修掉（其三）：Markdown 工具栏点完光标跳到末尾

**这是我上一轮笔记里的"已处理"实际没生效**——笔记写着「改完值后要在 `[value]` 的 effect 里
setSelectionRange 把光标放回插入内容上」，代码也确实那么写了，但**真机一量是失效的**：

```
选中「第一段」(0-3) → 点「加粗」→ 文本正确变 **第一段**
但 selectionStart = 12（= 末尾），正确应是 2-5
```

**根因**：`@uiw/react-textarea-code-editor` 是**延迟一个 tick** 才把新值写进 textarea 的，
而给 `.value` 赋值会把光标顶到末尾。子组件的 effect 先跑（注册了那个 tick），我的父级
effect 后跑、设好了 2-5，随后 uiw 的 tick 触发、覆写 `.value` → 光标回末尾。

**修法**：把恢复也放到 `setTimeout(..., 0)`（我的 effect 在 uiw 之后注册，所以 tick 更晚触发，
能盖过它），并记得 cleanup 清 timer。真机复验：`selectionStart: 2, selectionEnd: 5, focused: true` ✅

**教训（两条）**：
① **笔记里写"已处理"不等于真处理了**——只有量过才算。我上一轮正是靠"我记得处理过"跳过了验证。
② 跟第三方受控组件抢光标时，先确认它**什么时候**往 DOM 写值；同步的 effect 不一定够，
往往要晚一个 tick。
③ 这条**没有单测**（需要 DOM + timer，本仓 vitest 跑 node 且无 jsdom），
只有真机验证兜底 —— 记在这里以免以后误以为有回归保护。

## 反向扫描：所有消费 `description` 的地方（结论：无遗漏，门控是对的）

逐个过 `src/server|shared|pages|layouts` 里所有 `.description` 引用，找"带格式 vs 裸用"：

- **格式感知（安全）**：`FeedDb:581`、`FeedPublicJsonBuilder:318-319`（配
  `contentFormat ?? content_format`）、`extContentReview:202`、`extCategory:91/158/400`
  三处、`item-handlers:31` —— 都把 `content_format` 传给了 `bodyToPlainText`/`bodyToHtml`。
- **裸用但安全**：`extCategory:485`（`description.replace(/<[^>]+>/g,'')`）、
  `extBook:129`、`FeedPublicJsonBuilder:88/185`、`site-files/public.ts:37`
  —— **全部是书籍/频道简介，不是条目正文**。而书籍/频道正是拿不到 `content_format`
  的调用方（被 `canRecordFormat` 门控），永远不可能是 Markdown，按 HTML 处理正确。

⇒ **这不是"没找到 bug"，而是证实了那道门控的必要性**：正因为书籍/频道无法变成 Markdown，
这些裸用 HTML 逻辑的地方才是安全的。若当初没加门控，这条链就会静默漏出 `#`、`**`。

### 补上输出 schema 的 `content_format`（deploy49）

**是功能完善，而且是契约 bug**：`apiItemOutputSchema` **extends `apiItemInputSchema`**，
所以输出 schema 里**早就声明了 `content_format`** —— 契约承诺会给，但 `FeedPublicJsonBuilder`

### 加固 `content_format` 白名单脆弱点（deploy48）

原代码是**两个独立 `if`**：一个写 `description`（来自 `content_html`），一个写
`content_format`。任何一次改动都可能只删掉其中一个 → 格式丢失、前台打印原始 Markdown。

改成**一个判定、成对写入**（`Object.hasOwn(content_html) || Object.hasOwn(content_format)`），
行为完全不变（仍支持"只给格式不给正文"），但**结构上让两者无法被分开删**，注释写明它们一体。

**诚实说明**：这改动只是「更难误删 + 更显眼」，**不能真正防住删除**。
真正拦住删除的是已有测试 `tests/worker/api-item-service.test.ts:90`
（`data.content_format` 必须是 `"markdown"`）。
本次新增的一条（"reads an unmarked body as HTML"）**拦不住删除** —— 它断言的是
"没写格式时也必定读作 HTML"这个语义（`bodyFormat(undefined) === 'html'`），
属于**另一半路径的覆盖**，别误以为它能防回归。

顺带确认一个**能力缺口（非 bug）**：公开**输出** schema 不含 `content_format`
（只有输入有）。但 API 吐出的 `content_html` 已是渲染后的 HTML，客户端读回再写
天然还是 HTML，**不会出错**；只是读不到"原文是 Markdown"这个元信息。
要补的话是给输出 schema 加 `content_format` —— 需要时再说。

### code-review 双轴审核 `fix/rbac-conformance`（基点 4db3fb4）

两个并行子代理（Standards / Spec）。**Spec 轴的 5 条安全相关断言我逐条回源码复核，全部证实**：

1. **`content:article:delete` 从未强制** —— §8.1 与 ADR D-008 都要求；实测 `items/[itemId].ts`
   只有 GET，真实删除走 `feed.ts` POST（`feed.ts:74` 判 `status === DELETED`），
   而唯一闸门是 `feed.ts:140` 的 **`content:article:update`**。
   ⇒ **没有 delete 权限的 editor 照样能删章节**。真实授权漏洞。
2. **`must_change_password` 从未被设置** —— `0031` 不写 `ext_user_security`，
   全仓只有 `clearMustChangePassword`（只清不置）⇒ **428 闸门在生产上不可达**，
   D-010 第 3 步形同虚设。
3. **被吊销的设备永远无法恢复** —— `resolve.ts:97` 的 upsert 是
   `ON CONFLICT … DO UPDATE SET last_seen_at = excluded.last_seen_at`，**从不把 status 复位**。
   而 DESIGN §5 写"重登可恢复 active"、计划 §8 签名写 `status='active'` ⇒ 吊销即永久 401。
4. **RBAC 管理页本身没有闸门** —— `rbac/index.astro:17` 直接 `readRbacBoard(env.FEED_DB)`，
   只有 ajax 端点被守卫。T-10 备注明确要求页面也受保护。
5. **`exemptFromMustChange` 是死参数** —— 全仓零调用方；且**改密端点完全没有 guard**，
   所以"改密接口豁免 428"这条机制从未接线。

Standards 轴主要结论：`RbacApp` 用裸 `<button>/<input>` + 手写重复 className、未用 `cn`/共享原语
（AGENTS.md 有明文要求）；守卫样板在 13 个路由内联、11 个 webhook 用包装器，**两种机制不统一**；
权限目录双源（`0031` + `seed.ts`）必须同改；`ajaxRbacBoard()` 零调用。

**教训**：`content:article:delete` 这类"规格列了但端点不存在"的行，**不能靠"端点不存在"就放过**
—— 要顺着业务动作找真实入口（删除是 POST 改 status，不是 DELETE 方法）。
