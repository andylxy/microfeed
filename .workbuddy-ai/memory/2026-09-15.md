### 批改脚本的坑（本机 CRLF）

源码是 **CRLF**，而 Python 脚本里写的多行 `old` 串是 `\n` → 直接 replace 全不匹配。
正确做法：读入后先 `src = raw.replace("\r\n", "\n")` 再匹配，写回时
`f.write(src.replace("\n", "\r\n"))`（`newline=""`）。
另外**同一 throw 的缩进随上下文变化**（4/6 或 6/8 或 8/10 空格），按统一缩进写 old 串会漏；
漏了就先 `print` 出 missing 再单独补。脚本务必在发现 missing 时**先退出不写盘**，
否则会留下「改了一半」的文件（本次就是靠这点安全重试的）。

## 审计：只改语言显示，不改功能逻辑（用户复核后修订）

用户明确原则：**中文/英文只是语言显示，不得修改功能逻辑**；有疑问必须与 git 对比。
据此对整批 i18n 改动做了逐项 `git diff` 审计，查出并修复 3 类真实回退：

1. **纯文本 → JSON（响应格式被改）**。`localizedError` 会带
   `content-type: application/json`，但不少端点原本是 `new Response("...", {status})` 纯文本。
   已用 `git diff -U0 | awk` 把「所有被删掉的纯文本响应」按文件列出来逐条核对，改回文本：
   `api/handlers.ts` 19 处 + `feed/json.ts` 1 处（`Feed context unavailable`）、
   主题/草稿 GET 404、account 系列 `"Not found"` 共 10 处、`media-upload` 3 处、
   `ThemePreview` 2 处。
2. **响应头丢失**。`auth/bootstrap.ts` 的 404 原本带
   `content-type: text/plain; charset=utf-8`；`search.json.ts` 的 400 原本带
   `cache-control: private, no-store`。统一助手一度把它们吞了，已修：
   `notFoundResponse(request?, init?)` 与 `localizedError(..., init?)` 都支持透传
   `ResponseInit`（`{...init, status}`），由调用点补回原头。
3. **凭空新增 `statusText`**。`notFoundResponse` 初版固定输出 `statusText: "Not Found"`，
   但 `media/media.ts`、`feed/responses.ts` 多数 404 原本没有。已改为默认不加，
   只有原本就有的两处（`feedUnavailable`、`site-files/public.ts`）显式传入。

### 新增助手（与 localizedError 对称）

- `localizedError(request, key, status, params?, init?)` → **JSON** `{error: "..."}`。
- `localizedTextError(request, key, status, params?, init?)` → **纯文本**。
- 判据：**原本是 JSON 就用前者，原本是纯文本就用后者**。改之前先 `git diff` 看原样。

### 审计结论（确认无功能变更的部分）

- `middleware.ts`：`content-type`、`www-authenticate`、`401/404` 全部保留 ✅
- `page-handlers.ts` / `webhook-handlers.ts`：状态码 1:1 保留
  （400→400、409→409、422→422、503→503、404→404），且都是 JSON→JSON ✅
- `oauth/consent`：`new Response(translate(...), {` —— init 对象原样保留 ✅
- `pages/media/[...key].ts`、`media-upload` 的 `ALL`：`allow` 头与 405 保留 ✅
- 公开 404（`feed/responses.ts` 等）：`status` 404 与 `statusText` 保持，只换正文 ✅

### 键存在性与中英文一致性校验（又发现 2 个静默 bug）

`localizedError` / `localizedTextError` / `translate` / `AppError` 的键都是**裸字符串**，
`tsc` 查不出拼错或不存在的键；而 `translate` 查不到会**原样返回键名** →
用户界面会直接显示 `errors.theme.unknownPreviewView` 这种东西。所以必须单独校验。

**校验方法**（用 `node --import tsx` 跑脚本、import 真实模块，别手写正则解析 i18n 文件）：
- 键存在性：从 `src/**` 抽 `localizedError(request,"K")` / `localizedTextError(...)` /
  `translate("K")` / `new (AppError|PageRequestError|WebhookRequestError)("K")` / `t("K")`
  的键，逐个调 `translate(K)`，**返回值 === 键名即缺失**。
- 中英文一致性：`flatten(en)` vs `flatten(zhCN)` 比键集合 + 每个键的 `{{占位符}}` 集合。

**结果**：
- 键存在性：引用 1232 个键 → **发现 2 个缺失**
  （`errors.theme.unknownPreviewView`、`errors.theme.unknownPreviewDataSource`：
  只在 `ThemePreview.ts` 被引用、**从未在 en/zh-CN 定义**）→ 已补进 en/zh-CN 的 `theme`，
  复验 **0 缺失**。
- 中英文一致性：`en 1433 / zh-CN 1433`，双向无独有键，`{{占位符}}` **0 处不匹配** ✅。
- 全量测试复跑不变（3 失败仍为环境/既有），`tsc` 0 错误，`git diff --check` 0。

## 页面 FOUC（先英文后中文）根因分析 —— 已定位，待用户拍板方案

用户反馈「页面先显示英文，跟着刷新为中文」。定位结论：**服务端与客户端各有一套语言判定，
且都不读对方写下的来源**。

| 环节 | 判定依据 | 位置 |
|---|---|---|
| 服务端 SSR | **只看 `Accept-Language` 头** | `AdminShell.astro:93`、`middleware.ts:49/59/297`、约 25 个 `.astro` |
| 客户端 i18next | **只读 localStorage** | `src/client/i18n.ts:21-27` |

- `microfeed-admin-language` cookie：客户端**写**（`admin-language.ts:20-26`）、
  内联脚本**读**（`AdminLanguageScript.astro:12-17`）、**服务端从不读**。→ 服务端恒为 `en`。
- **内联脚本救不了**：它只改 `document.documentElement.lang`。主题能用这招是因为切 CSS class
  （`AdminThemeScript.astro:18`）；语言要真正重渲染文字，改 `lang` 属性不翻译任何字。
- **SSR 的 React 岛屿必然英文**：`AdminSidebar` 等 `client:load` 会被 SSR，而
  `src/client/i18n.ts` 在服务端无 `window` → `storedAdminLanguage()` 走 catch 返回 `"en"`，
  全局单例即英文。
- **主内容区不闪**：22 个页面用 `client:only="react"`，本就不 SSR，只出灰色骨架屏
  （`AdminPageFallback.astro`）。真正闪的是侧边栏、顶栏、`<h1>` 标题。

### 三个候选方案（已向用户列出优劣）

1. **只做服务端 cookie 优先**：约 25 处机械替换。修好 `.astro` 文本/`lang`/标题/面包屑；
   但侧边栏仍闪，且会出现**「中文标题 + 英文侧边栏」混排帧**，可能比现状更显眼。
2. **方案 1 + 外壳岛屿改 `client:only="react"`（推荐）**：8 处（5 个侧边栏 +

## 公开站点 4 处 `<h1>Not Found</h1>` 本地化

`404.astro`、`index.astro`、`search/index.astro`、`i/[slug]/index.astro` 各有一个降级分支
（隐藏公开站点 / 条目不存在 / 主题不支持），原来是硬编码英文 `<h1>Not Found</h1>`。

### 关键事实：降级分支里 `loaded` 是**加载成功**的

`unavailable` 来自 `shouldHidePublicWeb(loaded.content)` 这类**策略判断**，不是加载失败。
所以 `index` / `search` / `i/[slug]` 三处其实**能拿到 `loaded.publicFeed.language`**
（即站点自身语言，`PublicLayout` 也拿它当 `<html lang>`）——那本该是更贴合的来源。

但 `404.astro` 走的是 `loadPublicPageRoute()`，**该函数不返回语言**（内部加载了 feed 却只返回
`{kind: "not-found"}`），拿不到站点语言。要用它就得改 `PublicPageRouteResult` 这个共享类型。

### 决策：4 处统一用访客的 `Accept-Language`

抽成 `src/components/public/PublicNotFoundHeading.astro`（逻辑只写一处），内部
`languageFromAcceptLanguage(Astro.request.headers.get("accept-language"))`。

- 理由一：4 处里只有 3 处能拿到站点语言，**一条规则**比"两处用站点语言、一处用访客语言"更好维护。
- 理由二：与**公开 API 的 401/404** 规则一致（那批我已从 cookie 改回 Accept-Language）。
- 复用既有键 `pageTitle.notFound`：英文 `"Not Found"` 与原文**逐字相同**（不会改动英文可见文案），
  中文为 `"未找到"`。
- 备选方案（若日后想要"站点语言优先"）：给 `loadPublicPageRoute` 返回值加 `language`，
  再统一改成 `publicFeed.language ?? Accept-Language`。

### ⚠️ 起 dev server 的最终可用姿势（踩了很多次）

Vite 会在服务就绪后**二次优化依赖**并删除 `deps_ssr_temp_*`（近 2000 文件）→ 被 safe-delete 闸打死。
所以**必须把「启动 + 轮询就绪 + 立即抓取」写在同一条命令里**，抢在就绪窗口内：

```bash
node node_modules/astro/bin/astro.mjs dev --port 4321 --strictPort > /tmp/dev.log 2>&1 &
for i in $(seq 1 70); do sleep 3
  code=$(curl -s -o /dev/null -w "%{http_code}" --max-time 4 http://localhost:4321/admin/login/)
  [ "$code" != "000" ] && [ "$code" != "502" ] && break
done
# 立刻 curl，然后 kill
```
另：若 `.vite` 存在且提示 "vite config has changed"，先把它**整体 `mv` 走**让 Vite 全新创建，

## 收敛最后一个闪烁边界（本轮新增改动）

**问题**：服务端用 `Accept-Language`，客户端原先在「localStorage 与 cookie 都没有」时
直接用 `navigator.language`。两者**不总是等价**（隐私工具会改 `Accept-Language`；
某些环境缺该头时服务端回落 `en`，而 `navigator.language` 仍是 `zh-CN`）→
SSR 一种语言、水合后另一种 → 闪烁。

**修复**：客户端与内联脚本都改为**优先采用服务端已经渲染时用的语言**。

- `src/client/i18n.ts` 的 `detectBrowserLanguage()`：顺序变为
  **localStorage → cookie → `document.documentElement.lang` → `navigator.language`**。
  第三级正是服务端写进 `<html lang>` 的值，读它即与服务端对齐。
- `AdminLanguageScript.astro`：显式偏好（localStorage/cookie）都没有时，
  改为**保留服务端渲染的 `lang`**，不再用 `navigator.language` 覆盖它
  （否则会把 `<html lang>` 改成与已绘制文字不符的值）。

两级都加在 `navigator` **之前**，所以显式偏好仍然优先。

**仍未闭合的边界（已知、无法闭合）**：cookie 被浏览器禁用、而 localStorage 有显式偏好时，
服务端看不到该偏好 → 只能按 `Accept-Language` 渲染。服务端读不到 localStorage 是 Web 的固有限制。

## ⛔ dev server 在本沙箱里**不可重复运行**（已放弃重试）

那次成功是**运气**：curl 恰好落在「已 ready、尚未崩溃」的窗口内。之后连续 4 次尝试全部失败，
根因固定且不可绕过：

```
vite [optimizer] ...  →  Object.commit  →  rm(deps_ssr_temp_XXXX)  →  2003 文件  →  闸拒绝  →  进程退出
```

Vite 优化依赖时**先写临时目录、commit 时删除**，而那个删除**必然 >50 文件**，必然被闸拦下。
所谓「先 mv 走 .vite 让 Vite 全新创建」也救不了——全新创建同样会走 commit 删除。

**并且 `astro check` / `vitest` 与 `astro dev` 的 Vite 配置不同**，会让 deps 缓存失效、
触发 re-optimize → 又走一次 commit 删除 → 又崩。所以三者**不能交替跑**。

**结论**：需要 SSR/浏览器实证时，**一次成功的抓取就要把结论记下来**，不要指望能复跑。
或者改用「单条命令内启动 + 轮询就绪 + 立即抓取」（能提高命中率，但不保证）。
