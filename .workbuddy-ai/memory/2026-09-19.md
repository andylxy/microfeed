## 内容审核：设计方向纠正（分析 + 第 3 项已做）

**诊断**（写在 `.microfeed/内容审核-改版分析.md`）：
- **A** 审核被建模成「发布审批」（draft→submitted→approved 控制上下架），但需求是
  「**内容纠错**」——审的是阅读页呈现的内容，错了要改。

**方案**：新表 `ext_content_correction`（迁移 0024，含 submitted_by/reviewed_by/diff_data/proposed_data）；

## 修复：审核页两个 bug（同一根因）

## 修复：「无法恢复到该版本」—— 快照链断了（不是没实现）

用户报 restore 报错 `review.restoreFailed`（"无法恢复到该版本。"）。**功能是实现了的**，

## 待审链路断链分析（用户质疑「审核处处漏，等于没有用」—— 属实）

取证结论：**待审链路根本不存在**。

| 事实 | 证据 |
|---|---|
| 全仓无代码把 `reviewStatus` 置为 `submitted` | grep 只命中纠错字段 `submittedBy` |
| 后台没有「提交审核」按钮 | i18n 键 `review.submit` **从未被引用** |
| `review_status` 只是镜像列（派生） | `FeedDb.ts:585` 从 `_microfeed.reviewStatus` 派生 |
| **队列读的是实时 `items.data`** | `extReview.ts:171 SELECT id, data … WHERE review_status='submitted'` |
| 导入章节不设审核状态 | ImportChaptersApp 无相关代码 |
| 线上待审只有 1 条 | 由 API/直接写库偶然产生 |

**6 处写路径全都不碰审核**：后台编辑条目、API 更新/创建、删除、分卷看板、纠错应用、
版本恢复/导入。唯一入队方式 = 拿 API Key 在请求体塞 `_microfeed.reviewStatus:"submitted"`。

2. 最小止血：加「提交审核」按钮 + 队列展示提交快照（治标，改了仍不重新入队）。
3. 废弃闸门：队列改为「有未决纠错的章节」，只靠纠错+留痕+回滚兜底（与新定位一致，最省）。
