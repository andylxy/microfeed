## 工单 06 新后台页中文化 — 完成，并抓到一个真实 bug

### 审计结论：新增组件本身是干净的

对 4 个新组件（`ReviewQueueApp` / `ReviewDetailApp` / `ImportChaptersApp` /
`CategoriesApp`）复扫**中英文硬编码均为零**——它们从一开始就用 i18n。
（工单第 3 项要求的"残留英文 UI 串为零"因此天然满足。）

### 🔴 但抓到一个真实 bug：3 个导航标签没有翻译键

侧边栏用**动态键** `t(\`nav.item.${item.id}\`)` 渲染标签，而 `nav.item` 下
**只有最初 8 项**：

```
缺: nav.item.import_chapters  (工单 03 引入)
缺: nav.item.review           (工单 05 引入)
缺: nav.item.categories       (工单 02 引入)
```

⇒ 中文后台的侧边栏会把这 3 项**显示成键名本身**（`nav.item.review`）✗

**为什么之前没发现**：`i18n:check` 只扫**字面量** `t("...")`，
动态键（模板字符串）它看不见 ✗ —— 这是它此前的一个盲区。

### 修法（两层）

1. 补齐 3 个键（en + zh），顺序对齐 `NAV_ITEMS`
2. **给 `i18n:check` 加一条规则**：枚举 `NAV_ITEMS` 的每个 id，校验
   `nav.item.<id>` 能解析（`translate(key) === key` 即缺失）。
   **已实测有效**：临时删掉 `nav.item.review` 立刻报
   "navigation labels with no translation (1) - the sidebar would show the key itself"，
   还原后通过。

> 教训：**动态拼出来的 i18n 键是静态扫描的盲区**。凡是 `t(\`prefix.${x}\`)` 形式，
> 都要像这样枚举取值域来校验，否则界面会静默显示键名。
