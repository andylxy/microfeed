## 内容 API 设计烤问（grill-with-docs，进行中）

目标：给管理后台「内容」分组（`group_content`）下模块增加**受保护的读 API**，供外部按
标签→书→卷章→正文 逐级获取内容。

### 已查明的领域事实（实测，勿再重查）
- 「内容」分组（`group_content`）下 5 模块：`books`/`volumes`/`categories`/`all_items`/`import_chapters`
  （`migrations/0050`）。菜单由 `ext_menu` 数据表驱动（ADR-002）。
- 公开 API 现有 tag 仅 Feed/Items/Pages/Site Files/Search/Channel/Media，**无任何内容类端点**。
- 实体真相：**书 = `channels` 行**；**章节 = `items` 行**，靠 `data._microfeed.bookId` 关联（**非外键，是 JSON 标记**）；
  **卷不是实体**，只是 `items._microfeed.volume` 字符串；分类是 `ext_category` 实体。
- **「标签」不是实体**：`tags` 只在 `ExtCategory.ts` 注释里出现过一次，全仓无代码读写。
  用户所指标签 = **分类 category**（如 内经类/本草/伤寒/东方玄幻），管理员可增删。
- **`microfeed.genre` 是单值字符串**（categoryId），一书一类。
- `getBookChapters(db, bookId, baseUrl)`（`src/server/feed/extCategory.ts:509`）是**全表扫描**：
  取全部 published items 再在 JS 里比对 `bookId`（D1 拒绝嵌套 `json_extract`）。章节排序
  pub_date 主序、chapterNo 破同日平局（chapterNo 每卷重置）。正文在 `items.data.description`(HTML)。
- 权限码**已全部存在**，无需新建：`content:category:read` / `content:book:read` /
  `content:article:read`（章节）/ `content:volume:read`。

### 已达成的共识（用户确认）
1. 标签 = 分类 category，管理员维护、可增删。
2. **受保护**：走用户在管理页创建的 API 凭证 → 凭证取角色权限 → 校验，失败返错误码。
3. 第 2 步返回**书摘要**（非纯 ID），避免 N+1。
4. **只返回已发布（status=1）**，不含草稿/已删除。
5. 第 3 步返回**卷→章两级层级**（书 → 卷列表[卷名+章数] → 每卷章节列表），
   由服务端分组，不是前端本地分组（推翻我最初的扁平列表建议）。
6. 章节正文按需取：用户点列表中的章节 → 用章节 ID 取正文。

### ⚠️ ADR-0006 对抗性审查发现（2026-09-24，纠正初稿三处重大错误）

**1. API 基路径 = `/api/v1/`**（`API_BASE_PATH`，`src/shared/ApiVersion.ts`），非裸 `/content/`；
另有 legacy `/api/`（`LEGACY_API_BASE_PATH`，带 deprecation 头，落日戳 `@1785888000`）。
路由文件在 `src/pages/api/` **与** `src/pages/api/v1/` 两棵树。

**2. ⛔ 路由白名单是硬编码**：`src/server/api/access.ts` 的 `integrationSuffix()` 是**白名单函数**，
未登记的路径 → `apiPathDetails()` 返 null → `decideApiRequest()` 判 `not-found` → **直接 404**。
**新增任何 API 路径都必须在此登记**，否则代码写得再对也不可达。

**3. ⛔ 三个形似而完全不同的权限命名空间**（初稿混淆，是本次最大坑）：
| 命名空间 | 值 | **出处** | 首次提交 | 校验者 |
|---|---|---|---|---|
| OAuth scope | `content:read` / `content:write` | **上游自带** | `e273f6c` 2026-08-07 | `apiKeyScopes` |
| **API 集成权限码** | `api:content:read` / `api:page:read` / `api:media:read` / `api:site:read` | **自研**（非上游！） | `3ac9b4a` 2026-09-23 | `requiredApiPermission` + `resolveUserPermissions` |
| 管理后台 RBAC 码 | `content:book:read` / `content:category:read` / `content:article:read` / `content:volume:read` | **自研** | `3ac9b4a` 2026-09-23 | 页面 guard |
⇒ **API 端点只能用 `api:*` 码**；`content:*:*` 是后台码，API 路径**永不查询**。
`api:*` 种子：`migrations/0035_ext_api_permissions_seed.sql`（本地未提交）+ `src/server/rbac/seed.ts`。
`DOMAIN_RULES`（`api-permissions.ts`）按前缀映射，无匹配则 fallback `api:content:read`。

**3b. ⚠️ 同一 API 端点有三条鉴权路径，按请求头短路分派**（`src/middleware.ts:181/233/283`）：
| 请求特征 | 路径 | 权限模型 |
|---|---|---|
| `Authorization: Bearer mflc_…` | login-credential（`credential-bearer.ts`） | **RBAC 码** `api:*` |
| `X-Access-Key: …` | signed-call | **RBAC 码** `api:*` |
| `Bearer <其他>` / `x-microfeedapi-key` | **legacy bearer（上游，注释称 "left completely untouched"）** | **OAuth scope** `content:read/write` |
⇒ **风险**：①同一 key 换带法 → 授权语义就变；②`content:` 前缀被两个命名空间共用（scope `content:read`
vs 后台码 `content:book:read`），肉眼难辨；③**legacy 路径可绕过细粒度 RBAC** —— 任何持
`content:read` scope 的 key 走 legacy 即可读全部内容，`api:*` 码不参与判定。
⇒ **决策**：内容 API 必须**仅**接受 RBAC 路径（login-credential / signed-call），
对 legacy bearer 返 401/404（需在中件按路径判断）。
**`/api/ping` 是匿名端点**（签名即身份，不走上述三条）。

**4. 既有端点**：`/api/v1/items/{itemId}/` GET **已存在且已返回正文**（`getApiItem` → `jsonFeedResponse`，
JSON Feed 形状，状态含 PUBLISHED/UNLISTED/UNPUBLISHED=**含草稿**，无 volume/chapterNo）。
`/api/v1/channels/{channelId}/` **只有 PUT**（且仅 primary channel），无书列表端点。

**5. 可直接复用的取数函数**（勿另写）：
- `listCategoryNav(db)`（`extCategory.ts:361`）= `visible=1` + `book_count`，一次查询 ← 分类列表用它；
  ⚠️ `listCategories(db)` 是**后台用**、**不过滤 visible**，不可对外。
- `listChannelsByGenre(db, genre)`（`:376`）= `WHERE genre=? AND status=?` 走 `channels_genre` 索引，
  直接返回 `ChannelBookSummary[]` ← 标签下书籍用它。
- `listVolumeBoard(db, bookId)`（`extVolume.ts`）分组规则 ← 卷章目录用它（**需加"仅已发布"过滤**）。

**6. 实现硬约束**：改 `OpenApiDocument.ts` **必须同步 `OpenApiTranslations.ts`**，
否则 `tests/unit/openapi.test.ts` 红三条。E1 若选细粒度 `api:*` 码，需同步
`PERMISSION_CODES`(`Constants.ts`) 与 `src/server/rbac/seed.ts`（由 `admin-endpoint-guards.test.ts` 强制相等）。

### 两套码的作用面（不是重复，是三个不同面）
| 面 | 授权模型 | 用途 |
|---|---|---|
| 管理后台 UI（页面/ajax） | 后台 RBAC 码 `content:book:read` | 后台细粒度授权；`ext_menu.permission_code` 绑定（ADR-002） |
| API 集成（自研两条路径） | `api:*` 码 | API 集成细粒度授权 |
| **OAuth 授权服务器** + legacy bearer | OAuth scope `content:read/write` | 第三方客户端（CLI/MCP）经同意流程拿 token；**上游资产** |

⇒ **病根不是"两套码"，而是前缀撞车**（scope `content:read` vs 后台码 `content:book:read`）。
⇒ **不能取消**：OAuth scope 是 OAuth 协议层声明（`better-auth.ts` provider 配置 + `.well-known` + consent 页），
删它=拆掉第三方集成能力；后台 RBAC 码是后台唯一执法依据。
⇒ **可做的是"统一执法"**：把 legacy 路径的 scope 映射到 RBAC 码（`content:read` → `api:content:read`），
统一用 `resolveUserPermissions` 判定 —— 一套执法、两套声明，且**分叉最小**（优于删分支）。

### 三类凭证实体与线上使用量
| 认证方式 | 身份表 | 线上使用 | 说明 |
|---|---|---|---|
| legacy bearer（**上游**） | `api_keys.scopes`（OAuth scope） | `api_keys` **0** | 上游路径，我们只加了 signed-call 分支 |
| signed-call（自研，`X-Access-Key`） | `api_keys.secret_hash` + `ext_api_key_owners` | `ext_api_key_owners` **0** | HMAC 签名；防篡改+防重放；**从未被使用** |
| credential-bearer（自研，`Bearer mflc_…`） | `ext_login_credentials` | **1 条在用** | 裸 bearer；靠吊销+限流；**唯一实际在用** |

⇒ 收敛目标：**3 种认证方式 → 1 种**（credential-bearer）。

### 🧩 两种凭证 × 三条路径（关键澄清，2026-09-24 实测）

**轴一：凭证类型**（fork 点判据：全部**自研**）
| 凭证 | 创建入口 | 存储 | 用途 |
|---|---|---|---|
| **登录凭证** `mflc_…` | 账号设置页 / 用户管理页（`LoginCredentialsPanel`） | `ext_login_credentials` | ①**登录后台** ②**调 API**（bearer） |

**轴二：API 鉴权路径**（middleware 按请求头短路分派）
| 请求特征 | 路径 | 由哪种凭证触发 |
|---|---|---|
| `Authorization: Bearer mflc_…` | credential-bearer | **登录凭证** |
| `X-Access-Key: …` | signed-call | **API 凭证** |
| `Bearer <其他>` / `x-microfeedapi-key` | legacy（上游） | 上游 API key（0 把） |

**⇒ 登录页 `/admin/login/` 的两条线**（`AdminLoginApp.tsx`，`mode` = `"account"` | `"credential"`）：
- **账号线**：单字段「账号」，按**是否含 `@`** 分派 `authClient.signIn.email` / `signIn.username`（better-auth）→ 建会话
- **凭证线**：`mflc_…` → POST `ajax/auth/credential-login` → `handleCredentialLogin`
  → `verifyLoginCredentialToken`（含限流 + 同源 CSRF）→ **换一个 better-auth 会话**（`createLoginSessionCookies`）

**⇒ 同一把 `mflc_` 凭证有两种用法**：①在登录页用 → 换会话进后台（**不是** API 鉴权路径）；
②在 `/api/*` 带 `Authorization: Bearer mflc_…` → 走 **credential-bearer 路径**（无会话）。

**⇒ 推论**：删 signed-call = 删「API 凭证」整套（`api/credentials/` 页 + `ajax/api/credentials/*` +
`ApiCredentialsApp.tsx` + `ext_api_key_owners`），但**登录凭证必须保留**（它还要用于后台登录）。

### ⚠️ 删 signed-call 的依赖边界（实测，勿误删）
**两处共享物必须保留**，否则才真会波及 RBAC / bearer：

### 🧭 `api:*` 码能否删除/合并（2026-09-24 实测）
