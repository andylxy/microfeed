# 内容审核开关：默认关闭，关闭即驳回积压

## 背景

内容审核链（ADR-0003 的延伸，`extContentReview`）在每次仪表盘保存后：写审计行 → 插入 `pending` 审核版本 → `pinToLastApproved` 把 `items.data` 钉回**最早 pending 版本的快照**（旧内容），直到有人在审核队列点「批准」才放行。

这个门禁对单人写作站是一次自我折磨：作者保存后 toast 显示成功，但正文实际被钉回旧值，重开页面呈现"编辑丢失"——wangEditor 切换场景的 bug 报告因此被误诊为编辑器问题（真实病根是门禁回滚；wangEditor 的受控覆盖是另一个已单独修复的小 bug）。生产库曾因此积压两条 pending（作者的测试编辑停留在 `proposed_data`，从未上站）。

## 决定

1. **保留审核链模型**（审计行 + 检查点 + pending 版本 + pin 门禁），但改为**可选**。
2. 新增设置项 `settings.contentReview.enabled`（settings 表新 category `contentReview`），**默认关闭**：
   - **关（默认）**：保存立即生效。实现上走 `recordContentChange` 已有的 `openReview === false` 分支——审计行照写、检查点节奏不变，只是不插 pending、不跑 pin。
   - **开**：现有流程原样（保存 → pending → 批准才生效）。
3. **从开切到关的那一刻**，服务端自动把所有仍处 pending 的版本标为 `rejected`（`rejectChapterVersions`，并写 reject 审计行）。驳回是"保持正文现状"（pin 的现状即旧内容），不是发布积压内容。
4. `/admin/audit/[itemId]` 页面新增只读「审核版本」区块：列出该章节全部审核版本（id / 标题 / 卷 / 章节号 / 内容 HTML / 状态徽章 / 时间），含已通过与已驳回——review 队列只显示 pending，历史决策此前无处可见。区块零操作按钮。

## 考虑过的替代

- **默认开启**：保持现状行为，但默认行为应是"保存 = 生效"；审核是多人协作的重流程，不该让单人站默认承担。
- **关闭时自动批准积压**：等于让从未被审核的内容上站，违背门禁的初衷；驳回（保持现状）语义更干净。
- **audit 行逐条配对审核状态**（按 submitted_at 就近匹配）：配对脆弱；独立区块列出全部版本，天然完整。
- **删除审核链**：审计与检查点（版本可回溯、可恢复）是有价值的部分，只是 pin 门禁不该默认挡在单人作者面前。

## 后果

- 新装站点与现有站点（无 `contentReview` 设置行）升级后**默认保存即生效**，行为变化明确可见。
- 升级时已积压的 pending 不会自动消失：需在设置页开→关一次（触发自动驳回），或去审核队列手动处理。
- 审核开启期间，"保存成功但站点未更新"是预期行为；audit 页面的审核版本区块让这一过程可观测。
- 设置入口：`/admin/settings/#content-review`（设置页锚点区块 + 侧边栏新条目「内容审核」），权限沿用 `content:settings:manage`。
