# ADR-0002: 作者隔离 —— v1 单管理员，预留多角色扩展

- 状态：Accepted
- 日期：2026-09-16
- 决策人：用户

## 背景

原决策点 3 计划「每作者一把 API Key 限自己书」。核实 `src/shared/Api.ts` 发现：microfeed 的 `ApiKeyRecord.scopes` 仅 `["content:read","content:write"]`，**无 channel 绑定字段**；账户模型为单管理员（`auth_account` 单条登录）。因此「按书授权」的轻量方案在当前代码下**不可行**。

## 决策

- **v1（初始实现）：采用单管理员模型**——所有作者/编辑共用同一后台登录（或同一把全局 API Key），**不做按书隔离**。零额外代码、最快上线、升级最稳。
- **预留扩展路径**：架构上保留后续升级到多角色/多用户的空间。当真实需要「作者只能改自己书 / 审核员能审」时，再按 `ext_role` + handler 层守卫实现，不阻塞 v1。

## 理由（trade-off）

- 小说站初期通常由同一运营团队维护，单管理员足够；
- 自建角色层（`ext_role` + 中间件）工作量与 rebase 冲突大，违背「轻量起步、升级零冲突」总原则；
- 用户明确要求「当前按管理员实现最初始的实现」，并确认「后续可扩展多角色多用户」。

## 影响

- 移除原决策点 3「API Key 按 channel 授权」；
- `ext_role` 表与角色中间件**不进入 v1**（已在 §9 Phase 4 标注不做，本次确认）；
- 未来若需隔离，Q1 选项 B（handler 层 key→书 映射守卫）或 C（`ext_role` 中间件）仍为可选升级路径。
