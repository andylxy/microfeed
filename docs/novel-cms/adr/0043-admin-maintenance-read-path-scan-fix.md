## 决策

### D1｜后台与维护路径采用同一标准

`AGENTS.md` 的量化要求覆盖全部读路径。后台页面与每日维护任务的单次代价同样消耗远程额度；扫描起点无论来自页面请求还是定时清理，都按同一口径修复。

本决定与 ADR-0024 D3「Admin 侧不纳入」冲突。D3 以「量小且低频」为由排除后台路径；本次按用户要求扩大审计范围，webhook 事件源选择器的 LIKE 查询（9,506 行）与后台列表、登录日志、主题维护路径改变了该前提，纳入本 ADR 修复。`readAdminMenu`（62 行）与 `readRbacUsers`（4 行）的代价仍然为小表读取，维持 D3 的结论。

ADR-0024 的 D1 与 D3 已加指针指向本 ADR。

### D3｜分类筛选按书分片，并用 `INDEXED BY` 固定计划

- 仅按分类筛选时，先以 `SELECT id FROM channels WHERE genre = ?` 取出书 id（走 0023 的 `channels_genre` 索引，读取 5 条索引项并回表 5 行）。每本书一个分支，分支内是 `bookRef = ?` 等值条件、同一排序键与 `LIMIT limit + 1`，外层再按同一排序键归并。
- 分支参数为状态、书 id、分支 LIMIT 三项，另加游标（0、1 或 3 项）与 tcmKind（0 或 1 项），外层保留 1 个 LIMIT。分片大小 = `floor((D1_MAX_BOUND_PARAMS - 1) / 分支参数个数)`：默认 33 本；三项游标且不带 tcmKind 时 16 本；三项游标与 tcmKind 同时存在时 14 本。
- `INDEXED BY ix_items_book_ref_updated` 必须显式写出。带具体状态筛选、按 `created_at` / `pub_date` 排序时，planner 会改选 `items_status_created_at` / `items_status_pub_date`（`probe-round5.mjs`、`probe-review6.mjs` 的 `EXPLAIN`），按状态顺序扫描完整个状态再逐行比对书引用；本地 9,506 行全部是 `status = 1`（`probe-facts17.mjs` 的「items rows by status」），所以单分支读取 9,506 行，5 个分支合计按 5 × 9,506 = 47,530 行推得，超过旧单条语句的 9,506 行。
- 单条语句形态同样显式写出该 `INDEXED BY`：带书筛选（「仅书」与「分类 + 书」）时 `fromItems` 用 `items INDEXED BY ix_items_book_ref_updated`，计划的定位与排序都由该索引给出，不再需要临时 B 树（`probe-facts10.mjs`、`probe-facts7b.mjs`）；不带书与分类的查询不强制，planner 可继续用状态索引。仅分类的单条语句仍为 `SCAN items USING INDEX ix_items_book_ref_updated` + `USE TEMP B-TREE FOR ORDER BY`（`probe-facts10.mjs`），这就是分类筛选必须走分支的原因。
- 归并比较器复刻 SQLite 的 `ORDER BY 列方向, id 方向`。排序键与 id 都是 ASCII，JS 的 `<` 与 BINARY 比较一致；NULL 时间戳映射为空字符串，在 ASC 位于最前、DESC 位于最后。
- 残余上界：`updated_at` 排序由索引顺序直接给出，每分支读取满 `limit + 1` 行；`created_at` / `pub_date` 排序时索引只负责按书定位，该书全部匹配行进入临时 B 树，本地单本最多 2,964 行 ≈5.7 MB，分类内合计最多 4,127 行 ≈8.0 MB。每行投影触发 `book_title` 与 `category_id` 两个 channels 点查，105 行合计 210 次索引项与表行读取。

### D4｜tcmKind 索引的适用范围

`ix_items_tcm_kind_updated` 只在「不带状态等值筛选（默认「all」为 `status != ?`）+ 按 `updated_at` 排序」时被选用，这一组合是后台列表的默认排序与默认筛选。按 `created_at` / `pub_date` 排序时 planner 仍选 `items_bie_ming (tcm_kind=?)` 加临时 B 树；带具体状态等值筛选时改选 `items_status_updated_at`，`tcm_kind` 成为残留条件。分类分支内 `tcm_kind` 同样是残留条件，单本最多 2,964 行 ≈5.7 MB。

保留该索引的依据是默认组合的收益：8,066 行 ≈15.6 MB 降到 21 行 ≈40 KB（MB 与 KB 按 `items` 平均 1,935 字节/行推得）。其余组合的代价见 D3 与 D4 的残余上界；不为它们再新建「CASE 表达式 + 排序列」索引，那将再写入 9,506 行、约 540 KB。

### D5｜方剂引用要求 `bookId`

跨书 LIKE 每次按 `items_bie_ming (tcm_kind=?)` 读取全部 8,066 个 section 行（按 `items` 平均 1,935 字节/行推得 ≈15.6 MB），正文上的 LIKE 没有索引可用；多本书存在同名方剂（桂枝汤在 4 本书共 110 条引用：70 / 32 / 6 / 2，`probe-facts22.mjs`），跨书结果对编辑页面无意义。接口要求 `bookId`，缺失时返回 400（文案键 `errors.fang.referencesBookMissing`）；编辑器在方剂缺少 `_microfeed.sourceBookId` 时直接显示不可用状态，不发送这条注定失败的请求。单书路径以 0111 的 `ext_marker_citations` 点查为主，另行扫描本书草稿补齐编辑器视图：草稿查询的计划是 `SEARCH items USING INDEX items_book_kind (book_id=? AND tcm_kind=? AND status=?)`，本地 status=2 的 section 为 0 行，命中的行才读取 `data`。物化行全量读取（本地单本书单个方剂最多 70 条，桂枝汤；点查计划见 `probe-facts21.mjs`），按 `book_id, receiptNo, id` 合并后截取前 50 条。修复后的读取字节数按 `probe-facts18.mjs` 的 `dbstat` 取值推得：物化表 1,818 行 / 147,456 字节（平均 81 字节/行），`ext_marker_citations_lookup` 索引 90,112 字节 / 22 页；最大命中的索引步进约 3.5 KB（每个索引项按 90,112 / 1,818 ≈ 50 字节计）、回表约 5.7 KB，合并回表 `items` 最多 70 行约 135 KB、篇章标题最多 50 行约 97 KB，整请求约 240 KB（按 `items` 平均 1,935 字节/行）。

### D6｜事件源选择器取消 LIKE 回退

非空查询只走 `ext_admin_typeahead`；索引未创建或未回填时返回空候选，操作者可以清空搜索词浏览最近条目。LIKE 直查在稀有词与无命中搜索词上都要读取 9,506 行（0.19% 的日读取额度），按 5,000,000 行/日折算只够 525 次请求（9,506 × 526 = 5,000,156 行，超出额度）。

改走索引后的本地取值（候选数来自 `probe-facts18.mjs` 的 `MATCH` 计数，计时来自 `probe-facts20.mjs`：每轮新建连接、单轮 9 次取中位数、5 轮再取中位数；字节按 `items` 平均 1,935 字节/行推得）：`黄芪` 22 个候选 ≈43 KB / 0.123 ms（区间 0.114–0.124）；无命中搜索词 0 个候选、0 字节 / 0.287 ms；单字 `黄` 291 个候选 ≈563 KB / 2.632 ms（2.421–2.841），因为 `ORDER BY i.updated_at DESC, i.id DESC` 在 `LIMIT 50` 之前完成，宽泛搜索词会把全部候选回表。空搜索词走 `items_updated_at`（434,176 字节 / 106 页）读取 50 行 ≈97 KB / 0.128 ms。移除前的 LIKE 直查计时为稀有词 34.006 ms（33.809–35.808）、无命中 36.912 ms（36.246–41.964），两种形态读取行数都是 9,506。三个索引形态都低于 LIKE 直查的 9,506 行 / 18,395,136 字节，最宽的形态约为其 1/33。派生索引体积为 `ext_admin_typeahead` 及其 FTS5 影子对象合计 1,249,280 字节 / 305 页（`probe-facts20.mjs`）；该虚拟表由 `src/shared/ItemSearchSql.ts` 的建表语句在运行时创建、`prepareItemSearch` 回填，不在 `migrations/` 里，本次不新建索引。

### D7｜账号查重依赖写入路径统一小写

等值比较走 `auth_user.username` / `auth_user.email` 的唯一索引。Better Auth 1.6.26 的 admin create-user、admin update-user、username plugin 在写库前都转小写；`bootstrap.ts`、账号邮箱修改与 RBAC handlers 同样先归一化。`tests/worker/rbac-user-profile.test.ts` 断言混写输入写入数据库时为小写（创建账号 513 行，断言在 525–526 行；修改邮箱 371 行，输入 `Mail2@Example.COM`，断言在 387 行），并覆盖大小写冲突被拒（创建账号的用户名 529 行、修改账号名的用户名 667 行、修改邮箱 401 行，均 409）。

### D8｜维护清理使用 `NOT EXISTS`

`NOT IN` 会先物化子查询的整列；`NOT EXISTS` 让每条候选行按关联列点查，事件侧走 0140、端点侧走既有的 `webhook_deliveries_endpoint`。两种写法的删除语义一致的前提是关联列非空：`webhook_deliveries` 的 `event_id`、`endpoint_id` 都是 `TEXT NOT NULL`（`migrations/0017_webhooks.sql:122-123`），子查询不会产出 NULL 让 `NOT IN` 整体不成立。端点删除的外层 `deleted_at < ?` 用不上 `webhook_endpoints_status (status, deleted_at, updated_at)`（`status` 没有等值条件），仍需扫描 `webhook_endpoints`：本地 0 行 / 4,096 字节 / 1 页，行字节在空表上无法取样；候选行再按 `webhook_deliveries_endpoint` 点查。事件删除的外层走 `webhook_events_created (created_at DESC, id DESC)`。`webhook_budget_reservations` 的按 `created_at` 删除没有关联子查询可改写，由 0139 的范围索引把 `SCAN webhook_budget_reservations` 变成 `SEARCH ... USING INDEX ix_webhook_budget_created (created_at<?)`（本地 0 行 / 4,096 字节）。

`webhook_endpoints` 的残余扫描给出修复方案与采用条件：`CREATE INDEX ix_webhook_endpoints_deleted_at ON webhook_endpoints(deleted_at)`，创建索引的写入行数 = 建索引时的表行数（本地 0 行 → 0 行、占每日 100,000 行写入额度的 0%）；该索引尚未在任何环境创建，其形态按空表的索引页推得为 1 页 / 4,096 字节（与 0139、0140 在副本上的空表形态同值，`probe-indexes2.mjs`），此后每次端点写入多维护该索引一行。判定条件：部署后执行 `SELECT count(*) FROM webhook_endpoints` 取得远程行数 N，每日清理一次的读取为 N 行，单次占 5,000,000 行/日 的 N ÷ 5,000,000（N = 200 时为 0.004%）。0017 的 `webhook_endpoint_limit_insert` 触发器把存活端点数限制为 20 个，超出 20 的行只能是已软删除、等待本次清理的墓碑行。N ≤ 200 时维持扫描形态，不创建该索引；N > 200 时创建。

端点物理删除（`store.ts` 的 `purgeWebhookEndpoint`）的独占事件判定是同一类残余：一次性读 `SELECT DISTINCT event_id … WHERE endpoint_id = ? AND event_id NOT IN (SELECT event_id … WHERE endpoint_id <> ?)`，计划为外层 `SEARCH webhook_deliveries USING INDEX webhook_deliveries_endpoint (endpoint_id=?)`（K 次回表，K = 本端点投递数；该索引只有 `(endpoint_id, created_at)` 两列，取 `event_id` 必须回表）＋ `LIST SUBQUERY 1` 的 `SCAN webhook_deliveries` ＋ `CREATE BLOOM FILTER`（W 行，W = 保留期内全部投递；`probe-facts22.mjs`）。改成 `NOT EXISTS` 在本轮探针里不成立：子查询带上 `endpoint_id <> ?` 后没有等值前缀可用，计划是 `SCAN o`，代价从整表一次变成每条候选一次整表（`probe-facts22.mjs`）。成立的两步形态是「本端点候选（K 行回表）＋ `SELECT DISTINCT event_id FROM webhook_deliveries` 走 0140 的 `COVERING INDEX ix_webhook_deliveries_event` 取全部投递（W 条索引项、零回表）」，再在 TS 侧做集合差：代价从 W 次表行降到 W 次索引项，单项字节以 0137 的 `(device_id, last_seen_at DESC)` 索引作近似参照（`VACUUM` 副本实测 4,096 字节 / 51 项 ≈80 字节/项，两列比 0140 的单列 `event_id` 更宽，所以按它取上界；0140 在 `VACUUM` 副本上只有 1 页 / 4,096 字节，副本的投递表 0 行，除不出单项字节），W = 30,000（默认日上限 × 保留天数，推得值）时约 2.4 MB，占 5,000,000 行/日的 0.6%。更彻底的形态是把 0140 的索引改成 `ix_webhook_deliveries_event (event_id, endpoint_id)`：两条 `NOT EXISTS`（cron 与 purge）的探测都变成按 `event_id` 等值定位且无需回表，purge 代价为 K 条索引项加 D 条索引项（D = 候选事件的全部投递索引项，合计上界 = K），不再随 W 增长；该形状的创建写入行数 = 建索引时的投递表行数 W，占每日 100,000 行写入额度的 W ÷ 100,000，每次投递多维护一行索引。采用条件按 W 判定：`SELECT count(*) FROM webhook_deliveries` 取得远程 W，W ≤ 200 时三种形态的差别都在 0.004% 日读取额度以内，维持现形态；W > 200 时先做两步形态（零新索引），W > 10,000 时再把 0140 改建为 `(event_id, endpoint_id)`（此时整表物化的 30,000 行上界已到达 0.6% 日读取额度，而索引形态的 K + D 上界为 600,000 索引项 = 20 端点 × 30,000，占 12% 以内）。本轮未实施：`webhooks` 在已部署实例上未开通，本地投递表 0 行 / 4,096 字节，没有可实测的 W。

### D9｜版本列表索引的形状按 planner 实测选定

生产查询是「过滤 `deleted_at IS NULL` + 按 `package_id ASC, created_at DESC` 排序 + 四个投影列」。三种候选形状在只读副本上逐一验证：

- `package_id ASC, created_at DESC, id, name, version, deleted_at`（`deleted_at` 收尾）：不带过滤的形态去掉临时 B 树并覆盖，带过滤的形态仍走 `themes_deleted_at` 加临时 B 树（`probe-facts11.mjs`）。
- 同上五列 + `WHERE deleted_at IS NULL` 的部分索引：planner 不选用；`INDEXED BY` 强制后计划是 `SCAN themes USING INDEX ix_themes_versions_live`，非覆盖，谓词仍回表复查（`probe-facts12.mjs`、`probe-facts13.mjs`）。
- `deleted_at, package_id ASC, created_at DESC, id, name, version`（`deleted_at` 前置，0141）：`SEARCH themes USING COVERING INDEX ix_themes_versions_cover (deleted_at=?)`，无临时 B 树、不需要 `INDEXED BY`、不读取表页（`probe-facts14.mjs`）。

0141 只覆盖带 `deleted_at IS NULL` 的形态。当前唯一生产调用方 `src/server/webhooks/explorer.ts:208` 显式传 `false`，`listVersions` 的默认参数由 `true` 改为 `false` 后，不显式传参的调用同样处于覆盖索引形态；本仓库现存的调用方只有该生产调用与 `tests/worker/themes.test.ts:1017`、`:1044` 两处显式传参的测试，默认值本身不代表任何一次实际读取。`includeDeleted = true` 需要显式传参，只有测试调用，没有 `deleted_at` 等值条件，计划仍是 `SCAN themes USING INDEX sqlite_autoindex_themes_2` 加 `USE TEMP B-TREE FOR LAST TERM OF ORDER BY`；要一并覆盖需再增加一个 `package_id` 前置的索引（4,096 字节、写入 10 行），没有生产调用方，不新建。

## 影响

- 行为变化五处：方剂引用缺少 `bookId` 时返回 400；事件源选择器在派生索引未就绪时非空查询返回空候选；编辑器不再显示跨书书名（单书下没有第二本书）；方剂引用响应不再回填 `bookTitle`（单书下恒为方剂所属书，编辑器未使用）；账号查重由 `lower(列) = lower(?)` 改为列等值比较，存量混写行不再被查重命中（本地 0 行，远程核对语句见 D7）。
