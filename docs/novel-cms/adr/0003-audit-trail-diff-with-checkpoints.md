# ADR-0003: 修改留痕存储 = 字段级 diff + 周期性检查点

- 状态：Accepted
- 日期：2026-09-16
- 决策人：用户

## 背景

用户硬性要求"内容修改必须留痕"：原始内容、修改后的内容、何时改、谁改、改了什么，都要记录（对应 `ext_content_audit`）。
原设计（§7.2）采用「每次修改存整篇 `before_data` / `after_data` 前后快照」。评审指出：长篇小说一章被改上百次会产生上百条全量快照，`ext_content_audit` 表会无限膨胀。

- Q3 决策：**只存字段级 diff**（不存整篇快照），控制存储增长。
- 但原 §7.1「恢复上版 = 回填 `before_data`」依赖整篇快照，diff-only 下无法直接回填 → 引出 Q4。
- Q4 决策：**检查点 + diff** —— 每 K 次编辑另存一份完整快照作检查点，恢复时从最近检查点 + 前向 diff 重放。

## 决策

`ext_content_audit` 改为：
- 常规记录存**字段级 diff**（标题/正文/卷章号/标签等逐字段的增删改），而非整篇 `data` JSON。
- 每 K 次编辑（建议 K=20，可在设置调整）存一份**完整 `data` 快照作为检查点**。
- **恢复任意旧版本** = 定位该版本之前最近的完整检查点 → 向前重放 diff 序列 → 重建目标版本 `data` → 回填 item。

## 理由（trade-off）

- 满足用户"完整追溯"诉求，同时把存储从 O(全量×编辑次数) 降到 O(diff×次数 + 全量×1/K)。
- 写入时需计算 diff、恢复时需重放，计算/复杂度高于纯快照，但换来有界的存储增长（长篇小说可持续运营）。
- 检查点机制让"回到很早之前某版"依然可行，不牺牲恢复能力。

## 影响

- 修订 §7.2：`before_data` / `after_data` 全量 TEXT 字段 → 改为 `diff_data`（字段级差异，可为 JSON）+ 可选 `checkpoint_data`（完整快照，仅检查点行非空）。
- 修订 §7.1「恢复」逻辑：由"直接回填 before_data"改为"检查点 + diff 重放"。
- 审计详情页（§7.4）原本就计划做"字段级 diff 高亮"，与新模型天然契合。
- 设计文档 `novel-cms-design.md` 相关段落待共识达成后统一回写（grilling 期间不改主文档）。
