## microfeed 改造为「小说站 CMS」架构讨论（探索阶段，未动手）

用户想把 microfeed 改成按小说管理的 CMS：前端负责显示、后端管理类别/书/章节 + 内容审核，参考番茄小说(fanqienovel.com)布局。

### 已核实的 microfeed 能力边界（grep 全仓库确认）
- **无**阅读量/人气/排行榜计数（无 view/rank/popularity 字段）。
- **无**待审/审核/举报/下架任何机制（仅 AutosaveCoordinator 的 pending，非内容审核）。
- 账户体系只有「管理员 + API Key」，**无**作者/审核员/读者多级角色（ApiSchemas 仅见 administrator 概念）。

### 确立的实体映射
- 书 = Channel（title/description/icon/authors + `_microfeed` 加 连载状态/签约状态/分类ID/标签）
- 章 = Item（content_html/date_published/status + `_microfeed` 加 volume/chapterNo/reviewStatus）
- 分类 = 新增 `ext_category` 表（命名空间隔离）；卷 = `_microfeed.volume` 标签分组（不建独立表）
- 前端展示全走 `themes/feed-zh/*.mustache`（web-feed=首页/书主页、web-item=阅读页、web-search=搜索），零冲突
- 数据扩展全走 `_microfeed`（`.loose()` + `_microfeed: z.record(z.string(),z.unknown())` 是官方扩展口袋，不动 Schema/迁移）

### 内容审核方案（microfeed 完全没有，须从零建）
- 角色：起步复用 API Key 按 channel 授权（每作者一把 key 限自己书，冲突最小）；完整方案才新增 `ext_role` 表 + 中间件（中风险）
- 状态机：`_microfeed.reviewStatus`: submitted→approved→published；驳回 rejected(+理由)。配合现有 status（unpublished 草稿 / published 公开）
- 审核队列页、机审（写入口接第三方文本审核 API/关键词预筛）、举报(`ext_report`)+下架，均须新建
- 可借鉴 writing-agent-lab 的 HITL「审批门+人工确认」状态机思想，但技术栈不同（.NET+MAF vs Cloudflare Worker+D1），只借设计不搬代码

### 升级风险分级
- 零冲突：themes/feed-zh 展示
- 低：_microfeed 扩展字段
- 中（需 rebase，命名空间隔离）：ext_* 表 + 新 admin 路由（分类管理/审核队列/批量导入）；多级角色动 middleware
- 高（避开）：改 ApiSchemas 顶层 / OpenApiDocument SSOT

### 番茄小说真实首页结构（WebFetch 实测）
最新资讯 + 男/女频精选 + 排行榜(阅读榜/新书榜) + 题材分类(西方奇幻/东方仙侠/科幻末世/都市日常/都市修真/都市高武/历史古代/战神赘婿/都市种田/传统玄幻/历史脑洞/悬疑脑洞/都市脑洞/玄幻脑洞/悬疑灵异/抗战谍战/游戏体育/动漫衍生/男频衍生…)

### 本轮回应的设计要点：内容审核「留痕」+ 升级零冲突（用户硬要求：原始/修改/时间/谁/改了什么 都要记录，且不动核心）
- 审计留痕表 `ext_content_audit`（命名空间隔离，加性迁移）：字段 item_id(关联) / before_data(原始内容 JSON 快照) / after_data(修改后 JSON 快照) / created_at(毫秒时间戳=何时改) / actor_type+actor_id(谁改) / action(改了什么: create/edit/submit/approve/reject/takedown/restore/auto_flag) / reason(驳回下架理由)。展示时按 before/after 字段级 diff 出"改了什么"。
- 审核状态机仍走 `_microfeed.reviewStatus`(draft→submitted→approved/rejected) + 现有 status(草稿/公开)，零 schema 改动。
- 举报 `ext_content_report`（读者匿名举报→进审核队列）；分类 `ext_category`、计数 `ext_view_count` 同属扩展层。
- 写入拦截点：item 保存 handler 末尾 + 1 行 `extContentAudit.record(...)`，逻辑收口到 `src/server/feed/extContentAudit.ts`（独立模块）；核心唯一改动点即此一处调用，rebase 风险最小。
- 升级安全铁律：① 所有新表用 `ext_*` 命名空间 + 高序号加性迁移，与上游 IF NOT EXISTS 不冲突；② 不碰 ApiSchemas.ts/OpenApiDocument.ts SSOT（审计为 admin 内部，不进公开 API）；③ 快照存 data JSON 原文，上游改 item 结构旧快照仍有效；④ 展示全走 themes/feed-zh 零冲突。
- 用户明确：暂不动代码，先讨论定方案；审计留痕方向已确认（原始+修改+时间+谁+动作 五要素齐备）。

### grill-with-docs 评审 + 设计文档回写（2026-09-16 终轮）
用户用 `@skill:grill-with-docs` 要求：基于 novel-cms-design.md 厘清功能、明确可执行性及不足/需改进，并特别问"书/章/内容数据是否进 DB 还是文件、要求存 DB"。
- **事实核查（先查代码再决策，非提问）**：
  - 内容存储 = **D1 数据库**（items.data / channels.data 均为 TEXT，JSON.stringify 写入；FeedDb `_putItemToContentStatement` 558/609、`_putChannelToContentStatement` 523）；全仓库无"内容从文件读取"代码；microfeed=Cloudflare Worker+D1 无持久文件系统。**满足"必须进 DB"**。
  - `ApiKeyRecord.scopes` 仅 `["content:read","content:write"]`，**无 channel 绑定** → 原"API Key 按 channel 授权"方案不可行（重大可行性修正）。
  - `_microfeed` 是 `data` JSON 内部字段，非列 → 设计原 `WHERE _microfeed.reviewStatus='submitted'` 是**无效 SQL**（G2 硬 bug）。
- **6 项决策（grilling 一次一问，用户拍板）**：① 作者隔离=v1 单管理员（预留 ext_role 扩展）；② review_status/genre 落成 items/channels 真实列+索引；③ 留痕存储=字段级 diff+周期性检查点（可回任意旧版）；④ 批量导入=粘贴文本框+文件上传(R2)双来源；⑤ 分类=单主分类+多标签；⑥ 内容持久化=D1。
- **产出文档**：`docs/novel-cms/CONTEXT.md`（领域术语表）+ `docs/novel-cms/adr/ADR-0001`(内容持久化=D1) / `0002`(作者隔离单管理员) / `0003`(留痕diff+检查点) / `0004`(查询列)。主文档 `docs/novel-cms-design.md` 已整篇回写（修正 G2 SQL、补 6 决策、模拟数据改 diff_data、§11 决策索引指向 ADR）。
- **待改进项 G5（未决、建议）**：microfeed 已有 `content_text` 列，读者应可搜章节正文（非仅书名/作者）——已在 §5 标注为增强项，不阻塞 v1。
