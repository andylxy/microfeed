## 写入层评估：发现并修复派生列漂移（真 bug，高收益）

- 写入链：`saveInternalItem`（写 `data` + `content_text`/`review_status`/`pub_date` 派生列）
  → `recordContentChange` → `pinToLastApproved()` 把 `data` 钉回已确认版本。
  **原先只回写 `data`，派生列没跟着回滚** → 待审期间 `content_text`（FTS 搜索）仍是未确认正文；
  `review_status` 列与 `data._microfeed.reviewStatus` 不一致。
- 同样的问题在 `approveChapterVersions()`：**确认后只写 `data`，`content_text` 永远是旧正文**
  → 站内搜索搜不到已确认的新内容（不是缓存问题，是列永久不更新）。
- 修法：抽出 `writeItemContent(db, itemId, dataJson)` 同时写 `data` + 三个派生列
  （`pub_date` 用 `COALESCE(?, pub_date)` 兜底），pin 与 approve 两条路径都走它。
  恢复版本走 `saveInternalItem`，本来就是全列写，无需改。
- 回归测试：`extContentReview.test.ts` 两条（钉回 / 确认各一条），
  测试库 `items` 表补了 `content_text` / `content_text_updated_at` / `review_status` 三列。
  `tests/worker/api-item-service.test.ts` 的旧断言是**靠这个 bug 才通过**的，

## 第四处：自定义页面改动后书本页/分类页导航不更新

- `loadSiteNav()` 把自定义页面（`navigation_pages`）放进**每个**公开路由的页头；
  `index / book/[id] / category/[slug] / i/[slug] / search` 都会 spread。
- 但 `publicCacheTagsForPath()` 只在 `isStandalonePagePath()` 时打 `PAGES` 标签，
  而它匹配的是 `/^[a-z0-9]+(-[a-z0-9]+)*\/$/` —— **`/book/BkA1x9pQ2Lm/`（含大写）和
  `/category/<中文>/` 都不匹配**，所以这两类响应没有 PAGES 标签。
  `purgePageCaches()` 原来只清 PAGES / page(id) / ITEMS → 书本页、分类页的导航要等 TTL。
- 修法：`purgePageCaches()` 补 `PUBLIC_CACHE_TAGS.PUBLIC`（兜底标签，每条公开响应都带）。
  页面编辑是低频后台操作，全清的代价可接受。
- 附带结论：`PUBLIC_CACHE_TAGS.PUBLIC` 是**兜底标签**，`publicCacheTagsForPath()` 无条件
  加它，所以只清 PUBLIC 就等于全清（books / categories 接口就是这么做的，没问题）。
  反过来说，只清细分标签时必须确认目标响应真的带那个标签。

## 审计记录质量（用户反馈后修，2026-09-20）

### 一次编辑出现 3 个字段

- 现象：改一次正文，diff 显示 `updatedAtMs` + `description` + `contentText` 三条。
- 原因：`recordContentChange` 的 before/after 是**内部 item 形状**（`getItemJson` 的
  `{createdAtMs, id, status, pubDateMs, updatedAtMs, ...data, contentText}`），
  其中 `updatedAtMs` 是写时间戳（每次必变）、`contentText` 是 `description` 的纯文本副本
  （`FeedDb._putItemToContentStatement` 里有 `item.contentText = contentText;` 会在保存时
  **改写传入的 item 对象**）。两者都不是人改的内容。
- 修法：`computeDiff` 加 `NON_CONTENT_FIELDS = {updatedAtMs, contentText, content_text}` 直接跳过。
  注意 `computeDiff` 也供 `approveCorrection` 用，一起受益。

### 恢复产生一堆空白「版本恢复」记录

- 现象：点几次恢复就堆几行 `action=restore`、`diff_data='[]'` → 页面显示「该记录没有字段级改动」。
- 修法：`restoreItemVersionHandler` 改为 `computeDiff(现有, 恢复后)`：
  ① 记录**真实改动**（不再是空 diff，恢复行终于可审阅）；
  ② 改动为空则**整条跳过**（不写库、不记审计），返回 `{restored:true, unchanged:true}`，
     客户端提示「当前内容已是该版本，无需恢复」。
- 生产库里那 3 条空白 restore 行**已删**（用户确认后执行）：
  `DELETE FROM ext_content_audit WHERE action='restore' AND (diff_data IS NULL OR diff_data='[]');`
  删前先导出到 `.microfeed/backup-blank-restore-rows.txt`。
  复核：审计表 17 → 14 行，`blank=0`，**快照行仍是 6 条**（版本重建链未受影响）。
  ⚠️ 全库当时也只有这 3 条空 diff，其他 action 的记录都带真实改动。

## ⛔ 用户明确的不变量：审计记录只增不删（版本管理的账本）

- 原话：「版本恢复后，相关记录不能清空或删除，保持好作为版本记录管理」。
- **恢复版本 = 只新增一条审计行，绝不清理既有历史。** 这是版本管理的前提：
  `rebuildItemVersion` 从最近的快照往前回放，链上断一行可能让后面所有版本都不可恢复。
- 代码现状已满足（`ext_content_audit` 全仓只有 INSERT，无 UPDATE / 无 DELETE）；
  已加架构守卫 `tests/unit/source-architecture.test.ts` → "keeps the audit trail append-only"，
  禁止 `DELETE/UPDATE ext_content_audit` 与 `DELETE ext_content_review`
  （待审行的 `UPDATE status` 是合法必要的，不在此列）。
- 页面 `audit.intro` 也写明「只增不删」，让读者知道它能作为版本依据。
- ⚠️ 这次的教训：之前我删掉 3 条空白 restore 行（用户当时同意了），但按新不变量
  **以后不要再删审计行**；真要清理必须先问。备份在 `.microfeed/backup-blank-restore-rows.txt`。

### ⚠️ 组合筛选恒返回 0：SQL 占位符与 bindings 顺序不一致（提交 `2149b7f`）

- 现象（用户给的复现，非常关键）：

- **真因**：`WHERE ${where}${cursorClause}${categoryClause}${bookClause}` —— SQL 里
  **分类在前、书本在后**；但代码先算 bookClause 先 `bindings.push(bookFilter)`，再
  categoryClause push。两个 `?` 拿反 → 分类子句拿到书本 id（与 `channels.genre` 比，必然不
  匹配）→ 恒 0 行。**单独用任一条件都对，所以之前完全没暴露。**
- 修法：clause 计算顺序与 SQL 占位符顺序严格一致（categoryClause 在前，bookClause 在后），
  并加注释警告这个顺序不能动。
- ⚠️ 测试教训（最重要）：**我之前的用例只分别测了「只有 bookId」和「只有 categoryId」，
  从没测过两者组合**——而组合才是这个功能的实际用法。改完必须验证测试在旧代码下**会失败**
  （我临时把顺序改回去跑了一遍，确认用例确实报错，才敢说它是有效测试）。
- 教训：**多个可选筛选条件组合时，一定要有一条「全部条件同时生效」的用例。**
  另外「改了 SQL 拼接却没同步 bindings 顺序」这类错误，单条件测试 100% 抓不到。

- `src/server/items/search.ts:385`、`src/server/webhooks/store.ts:365`、

## Markdown 编辑器（提交 `b584656`）

## ⛔ 正文格式：按原形保存，渲染推迟到显示时（提交 `14f3786`，推翻上一版设计）

用户指出上一版（MD 保存时转 HTML）会让 MD 反复转换后丢失——**这个批评是对的**。
HTML→MD 是有损的；而且一旦用可视化/HTML 模式编辑，原文就没了。

**新规则（务必遵守）**：
- `data.description` 存**作者写的原样**：Markdown 写的就存 Markdown，HTML 写的就存 HTML。
- `data.content_format` = `"markdown" | "html"`；**缺失即 html**（所有旧条目都符合，零迁移）。
- 渲染**只在显示时**做，绝不在保存时做：

## 正文 diff 改成按段落对比（提交 `ac8447e`）

- 实测生产库：**所有 `data.description` 都是单行（`newlines = 0`）**——Quill 输出本身
  没有换行。而 `toLines` 只按 `\n` 切 → 整章被当成一行 → 审计/审核的 diff 显示一个巨大的
  `-` 行和一个 `+` 行，**看不出改了哪句**。这恰恰是最需要看清的东西。
- 修法：无换行且含块级标签时，按 `</p> </div> </li> </h1-6> </blockquote> </tr>` 与 `<br>`
  切块 → diff 变成逐段（上下文 / `-第二段` / `+第二段改了` / 上下文）。
  Markdown 渲染出的正文自带换行，不受影响；纯文本也不受影响（都有反例测试）。
- ⚠️ **不要用后行断言 `(?<=...)`**：旧版 Safari 不支持，会在**解析 bundle 时直接抛错**
  （整个前端挂掉）。用 `replace(正则, "$&\n")` 再 `split("\n")` 达成同样效果。
- 测试踩坑：React SSR 会在相邻文本节点间插 `<!-- -->`，且 HTML 会被转义成 `&lt;`；
  断言前要先剥注释、反转义，否则 `toContain("-<p>...")` 永远失败。

## Markdown 编辑器到底怎么渲染（回答用户疑问）

- Markdown 模式是**纯文本框**（`AdminCodeEditor`），**不是 Quill**。用户一度以为是 Quill，需澄清。
- 渲染发生在两处，都是**显示时**，编辑框本身不渲染：
  1. 后台：`AdminMarkdownEditor` 有**实时预览**（默认开启，用 `renderMarkdown`），就在输入框下方。
  2. 前台：阅读页由 `FeedPublicJsonBuilder` 用 `bodyToHtml` 渲染。
- 若用户想要"编辑区直接所见即所得"：那需要保存时把渲染后的 HTML 转回 Markdown，**有损**，正是用户担心的丢失问题。折中方案是保持源码编辑 + 常驻/分栏预览（无损）。
