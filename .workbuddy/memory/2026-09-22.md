## 分析 api/explorer 接入「开放接口签名调用（无 JWT）」

- 参考：XiHan BasicApp 开放接口 = HMAC-SHA256 签名调用，头 `X-Access-Key`/`X-Timestamp`/`X-Nonce`/`X-Signature`，时效 ±5min（300s），受保护前缀 `/api/openapi`，自测端点 Ping/Echo，凭证 `ak_`+`sk_`（sk 仅哈希存）。
- 项目现状：`src/pages/[adminPath]/api/explorer/index.astro` 是 API 探索器 UI（用 Bearer/JWT 经 `/api/auth`）；真实公开 API 在 `src/pages/api/v1/*`。鉴权门禁在 `src/server/api/access.ts::decideApiRequest()`（读 `Authorization: Bearer` 或 `x-microfeedapi-key` → `api_keys` 表查 scopes，`settings.enabled` 总开关）。API Key 体系 `src/server/api/api-keys.ts` 用 `mf_` 前缀单值密钥存 `api_keys`（明文）含 `scopes`（`content:read`/`content:write`）。
- 升级安全红线（与 RBAC 一致）：不碰 `better-auth.ts`/`createMicrofeedAuth`；不动 `auth_user`/`auth_session`；新表全 `ext_`、序号 ≥0032；仅纯追加 `access.ts`/`middleware.ts`/`Api.ts` 等既有文件。
- **用户纠正（重要）**：`api_keys` **只作登录凭据/签名密钥源**，其 `scopes` 字段**不参与授权判定**；授权必须走 **RBAC 角色权限**（`ext_roles`/`ext_permissions`/`ext_user_roles`）。之前草稿里"调 `apiKeyScopes` 复用 scopes 授权"是错的，已作废。
- 修正后设计：① 签名（HMAC-SHA256，用 `mf_` api_key 作密钥）只负责**认证**（证明持有登录凭据、确立 `api_key_id`）；② 因 `api_keys` 无 `user_id`，需新建 `ext_api_key_owners(api_key_id PK/FK→api_keys.id, user_id FK→auth_user)` 把凭据绑定到 RBAC 主体（不 ALTER `api_keys`）；③ **授权** = `resolveUserPermissions(db, userId)` → `Set<权限码>`，复用与管理后台同一套权限码（`content:book:create` 等）+ `requirePermission` 语义（401/403），与既有 admin ajax 守卫一致；④ 防重放复用已存在的 `ext_replay_nonces`（RBAC 建的）。新增 `src/server/api/openapi-signing.ts`（verifySignature/nonce/resolveOwner），在 `decideApiRequest` 前置一个签名分支（少数追加行），自测端点挂 `/api/openapi/ping`、`/api/openapi/echo`。
- 待用户拍板：① 提取/派生 `X-Access-Key` 的方式（直接用 `api_keys.id` vs 另发 `ak_` 派生键）；② 是否只做自测端点还是把 v1 集成端点也纳入签名可调用。尚未实现，仅分析。

- **核心难点：不改 `createMicrofeedAuth` 的前提下「按 userId 建 better-auth 会话」**
  - 探针实测：`auth.api` **没有** `setSession`；`impersonateUser` 需管理员会话（不适用）。

  - cookie 算法（照搬 `better-call` 的 `signCookieValue`/`serializeSignedCookie`）：

    属性输出顺序 `Max-Age; Domain; Path; HttpOnly; Secure; SameSite`。
  - **护栏测试**：把生成的 cookie 喂回 `auth.api.getSession({headers:{cookie}})` 断言返回该 userId ——

### 第四轮（用户给出正式布局规范）：登录页改为「三段式」

用户规范：① 账号/凭证 tab 在顶部；② 邮箱+密码是中间内容，切凭证时**只替换中间**，顶部与底部不变；
③ 登录 / 或 / 使用通行密钥登录 是底部，**两个 tab 共用同一个登录按钮**。

- `AdminLoginApp.tsx` 重写为：`<div role="tablist">`（顶部）→ **一个 `<form>`** 包住中间与底部 →
  中间 = `<div className="grid">` 内两个 `<fieldset>`（都 `col-start-1 row-start-1`，非活动的加
  `invisible` + `disabled`）→ 底部 = 共享 `type="submit"` 登录按钮 + 「或」+ 通行密钥按钮。
- **为什么必须是同一个 form**：登录按钮被两个 tab 共用，按钮只能提交它所属的表单；若维持两个 form，

- **为什么隐藏那半要用 `<fieldset disabled>`**：同一个 form 里，`visibility:hidden` 的

  → 菜单过滤必须同样处理，否则会把老管理员锁在外面；② `AdminShell.astro` **从不把权限集传给任何组件**

- **两条实现路线**：A 服务端过滤（在 `AdminShell.astro` 把权限集传给 `getAdminNavigationItems`，
  无权限项直接不渲染 —— 推荐，无闪烁、不把权限模型下发到浏览器）；B 客户端过滤（下发权限集后组件内过滤，
  与 rbac 页面"防止仅登录就读到整个权限模型"的意图相悖，且有首屏闪烁）。
- **方案文档** `.scratch/microfeed-rbac/admin-menu-rbac-plan.md`（工单 #111–#118）：16 项菜单↔权限码
  完整对照、A 路线逐处改动、14 页守卫补齐清单。
- **查证到的两个关键点**（写方案时才量出来）：
  ① **editor 角色没有任何 `content:article:*`**，而 `ajax/feed.ts:148-153` 要求 `content:article:update`
     ⇒ editor 当前**根本无法编辑/新建章节**（既有缺陷）；若按 article:read/create 过滤菜单，editor 会
     连"内容列表/导入章节"都看不到 ⇒ **补授权必须排在菜单过滤之前**。
