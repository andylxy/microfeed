## 方剂「组成缺失」性质分层（修正 2026-10-02 规范 §4 的错误表述）

**背景**：用户质疑「10001/10002 宋版仅 1–2 首缺 → ❌ 不能补，为什么不能补」。实测后确认我原来的理由说得不准，特此更正。

### 实测结论：三类缺失性质完全不同，不能一概而论

判据 = **空组成的方剂，其正文（`description`）里有没有 `$u{` 标记**：

| 书 | 频道 | 方剂数 | 空组成 | 其中正文**有** `$u{`（有数据可补） | 正文**无**标记（真无米） |
|---|---|---|---|---|---|
| 1001000 桂林古本 | `5IGM9t76quT` | 329 | 322 | **316** | 6 |
| 9050000 金匮·人纪 | `Kcb7X2K5LTh` | 49 | 47 | **46** | 1（獭肝散） |
| 9040000 伤寒·人纪 | `XNK0VFX39Xv` | 111 | 2 | **1** | 1（土瓜根「方缺」） |
| 10001 宋版伤寒 | `q6u5siNb2hT` | 113 | 1 | **0** | 1（禹余粮丸「(佚)」） |
| 10002 宋版金匮 | `ydyQltIuQv6` | 202 | 2 | **0** | 2（杏子汤/黄连粉「方未见。」） |

### 关键事实：宋版 3 首是源数据本身标注失传，不是导入丢失

源 `ctwh/Fang.sql` 原文（白纸黑字）：
- `(39, '禹余粮丸', 38, 0, 10001, '39、$f{禹余粮丸} (佚)', …)` → `YaoCount=0`
- `(238, '杏子汤', 124, 0, 10002, '125、$f{杏子汤} 方未见。', …)` → `YaoCount=0`
- `(282, '黄连粉', 168, 0, 10002, '169、$f{黄连粉} 方未见。', …)` → `YaoCount=0`

netcore `GetBookIdFang?bookId=10001` 对这 3 首同样返回 `yaoCount="0"`、`yaoList=[]`、`standardYaoList=[]`。
⇒ 三方（源 dump / netcore / 本地）完全一致，**不是本地导入 bug**。

### ⚠️ 修正：原来把「不能补」一律归给 golden 约束是错的

正确分层：
1. **10001/10002 宋版 3 首 = 事实判断「无数据可补」**（源标「佚/方未见」，正文 0 个 `$u{}`）。
   若硬补只能跨书搬同名方（如桂林古本 FangId=717 黄连粉含黄连/甘草），属**同名不同方、跨书伪造**，且立刻产生 3 处 golden MISMATCH。
2. **1001000 桂林古本 316 首 = 策略判断「有数据但补了破坏对齐」**：
   netcore 对 1001000 返回 329 首、**仅 7 首有 `standardYaoList`**，本地 7/329 与之逐字对齐。
   补 316 首后本地会变成 323/329 → 打破 golden。**这条应由用户重新拍板**（数据完整性 vs golden 逐字对齐）。
3. 9050000 金匮·人纪 46 首、9040000 伤寒·人纪 1 首：**netcore 对这两本书 `GetBookIdFang` 返回 0 首**，无可比对象 → 补了不产生 MISMATCH，可安全补。

### 附带发现（netcore 宋版方剂的归属与本地不同）
netcore `GetBookIdFang?bookId=10001` 返回 **315 首**（= 113 + 202），`?bookId=10002` 返回 **0 首**
⇒ netcore 把宋版伤寒+宋版金匮合并挂在 10001 下。本地按书拆成 113 / 202，总数 315 吻合。
（属已记录的 golden 遗留差异，非新缺陷。）

### 排查套路（可复用）
判定「某首方剂的组成是真丢失还是只是没被提取」的标准动作：
```sql
SELECT book_id, json_extract(data,'$.title'), json_extract(data,'$._microfeed.no'),
       substr(coalesce(json_extract(data,'$.description'),''),1,70)
FROM items
WHERE tcm_kind='fang' AND status!=3
  AND COALESCE(json_array_length(json_extract(data,'$._microfeed.fangYaoList')),0)=0
  AND COALESCE(json_extract(data,'$.description'),'') NOT LIKE '%$u{%';
```
→ 结果里的方剂才是**真正补不出来**的（正文无 `$u{}` 标记）。其余都是有数据但 `build.ts:665` 只认 `FangBody` 表而漏提取。

### 遗留
- 9050000 有 6 首「声明味数 ≠ 解析味数」需人工核对（防己黄耆汤 4/8、鳖甲煎丸 23/25、蜀漆散 3/4、乌头汤 2/7、獭肝散 1/0、皂荚丸 3/2）。

2. **硬编码兜底层（窄口径）**：`DEFAULT_APP_LOGIN_CREDENTIAL`(49-50) 那串 `mflc_…655a82` 只在 `middleware.ts:247-249` 一个条件下注入——**请求走 `/api/AppBookRequest/*` 且请求没带 Bearer 时**，才用这默认 key 兜底；其他 `/api/*` 路径 `defaultKey=null`，必须自带合法 Bearer 否则 `unauthorized`。

### 关键推论（轮换复杂度）
- **轮换"库里的真实凭证 / 用户登录后的 key"= 零改动零部署**（动态，纯 DB）。
- **唯一逼你动代码的**：换"兜底默认值"本身——Worker 第 50 行（+重部署，或改成读 `env.DEFAULT_APP_LOGIN_CREDENTIAL` 一劳永逸免重部署）+ Android `SecurityConfig.sApiKey`(47，不是第4行)（+重发 App）。但后者在"用户登录后走自己的 key"模型下只是冷启动兜底，App 端打包的密钥逆向必出，安全靠"库里随时能吊销"。
- 结论：**整体不复杂，多数轮换场景根本不用重部署**。早前"改两处+重部署+重发"是 worst case，已更正。

### Android 侧事实
`InterceptorHelper.loginBearer()`(141-149) 返回 `SecurityConfig.getApiKey()` = 写死的 `sApiKey`(47)，即 App 默认发出的 Bearer；有 `setApiKey()` 接口但尚未被调用（仅作初始值）。`git` 已推 `feature/microfeed-adapt`（含该硬编码 key，用户拍板 B 豁免 AGENTS.md 规范照推）。

### 待办（未做）
- 落地轮换前应先去 D1 把绑定 `app:mobile:access` 的那行 `mflc_…655a82` 凭证挖出来，确认归属用户与吊销状态。

### 已实施：移除写死兜底默认值（2026-10-03 15:45，用户直接指令）

用户要求：删掉 `credential-bearer.ts:50` 写死的 `DEFAULT_APP_LOGIN_CREDENTIAL`；`/api/AppBookRequest/*` 请求**没带 Bearer（无 mflc*）时直接 401**，不再注入默认 key。

**改动（2 文件）**：
- `src/server/api/credential-bearer.ts`：删除 `DEFAULT_APP_LOGIN_CREDENTIAL` 常量及其 JSDoc；`decideLoginCredentialApiRequest` 删除 `defaultKey` 形参与 `?? defaultKey` 兜底，`token = providedLoginCredential(request)`，无 token 即 `unauthorized`。
- `src/middleware.ts`：删除 import；判定分支改为 `if (providedLoginCredential(request) || pathname.startsWith("/api/AppBookRequest/"))`，AppBookRequest **始终走 login-credential 分支**（无 Bearer 时 token=null → `unauthorized` → 401）。保留 `else` 旧 API-key 分支给其余 `/api/*`。

**为什么这样写（关键判据）**：不能把"AppBookRequest 无 Bearer"丢给 `else` 的 `decideApiRequest`——它对非 integration 路径回 `not-found`(404) 而非 401（`access.ts:175-176`）。强制 AppBookRequest 进 bearer 分支才能保证回 401，且符合 ADR-0006「login-credential-only」。

**验证**：`yarn typecheck` 0 errors/0 warnings/5 hints（hints 是无关测试既有）；定向测试 `login-credential.test.ts`(28)+`password-setup.test.ts`(4) 全过（32/32）。注意：Android 端 `SecurityConfig.sApiKey`(47) 仍写死、且 `InterceptorHelper.loginBearer()` 默认就发它当 Bearer → App 仍会带 Bearer，行为不受影响；仅"完全不带 Bearer 的 AppBookRequest 请求"现在才会 401。

**副作用**：依赖"服务端默认 key 兜底"的旧客户端（不带 Bearer）将失效→401。属用户接受的预期后果。
